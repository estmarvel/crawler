# Project 表与 JSON 字段对应及 current_status 判定规则

## 1. 文档范围

本文档说明：

- 爬虫 JSON 及项目关系映射如何生成 `project` 表；
- `project` 每个字段对应哪些 JSON 字段；

## 3. 项目识别与公告合并规则

### 3.1 项目主键规则

业务上的项目唯一标识使用“项目编号”，不使用项目名称作为唯一标识。

复合编号示例：

```text
E1401005107101294001；SXLS-2025028
```

拆分结果：

```text
项目编号：E1401005107101294001
招标编号：SXLS-2025028
```

`project.project_code` 只保存项目编号。

### 3.2 公告匹配优先级

普通公告按照以下顺序匹配项目：

1. JSON 结构化字段中有明确项目编号；
2. 公告正文中有“招标项目编号”或“项目编号”；
3. 公告有招标编号，并且该招标编号唯一对应一个项目编号；
4. 去除标段后的项目名称一致，并且招标人/采购人一致；
5. 去除标段后的项目名称一致，并且招标代理机构一致；
6. 仍无法唯一确认时进入人工确认，不自动写入项目关系。

招标计划先使用去除公告类型、标段等后缀后的标准化项目名称，在同平台招标公告中匹配：

1. 项目名称唯一对应一个项目编号时，并入该项目；
2. 同名项目有多个编号时，增加招标人名称进行唯一确认；
3. 找不到同名项目或无法唯一确认时，仍建立独立项目，`project_code=NULL`、`current_status=PLAN`。

当前25条计划中，2条匹配到已有项目编号，23条建立独立计划项目。

### 3.3 标段名称标准化

以下名称应归入同一个项目编号：

```text
2020一2022年临时占用林地森林植被恢复造林项目施工(001,002标段)
2020一2022年临时占用林地森林植被恢复造林项目施工(001标段)
2020一2022年临时占用林地森林植被恢复造林项目施工(002标段)
```

用于辅助匹配的标准化名称为：

```text
2020一2022年临时占用林地森林植被恢复造林项目施工
```

标准化过程只删除可明确识别的数字标段、公告类型、延期、变更、终止等后缀，不删除“（一期）”“（EPC）”“（暂估价）”等项目名称组成部分。

### 4.1 province、city 提取规则

地点原文始终原样保存到 `location_text`。`province`、`city` 是从同一字段生成的标准化摘要，不会覆盖原文。

标准示例：

```text
项目地点：中国-山西省|太原市
province：山西省
city：太原市
location_text：中国-山西省|太原市
```

当前只识别山西省及其 11 个地级市：太原市、大同市、阳泉市、长治市、晋城市、朔州市、晋中市、运城市、忻州市、临汾市、吕梁市。

具体规则：

1. 原文包含`山西省`或`山西`时，`province`标准化为`山西省`；
2. 先用`|`拆分地点，按照从左到右的顺序，选择第一个包含明确地级市的分段；
3. 如果选中的分段用`、`并列多个地级市，所有城市均按原顺序保留，并以`、`连接后写入`city`；
4. 选中前面的分段后，忽略后续`|`分段中的城市，即前面的详细项目地点优先；
5. 原文只有明确地级市，例如`吕梁市`，可唯一反推为山西省，写入`province=山西省`、`city=吕梁市`；
6. 只有县、区、道路或`招标人指定地点`等描述且没有明确地级市时，不从地址文字猜测城市；
7. 所有空值和无法识别的记录写入`reports/project_location_anomalies.json`；每个异常项目同时保存关联公告的详情页链接、公告 ID、公告类型、标题及该公告的地点原文，便于人工核对。

多城市示例：

```text
中国-山西省-晋中市|太原市
-> province=山西省，city=晋中市

中国-山西省|太原市
-> province=山西省，city=太原市

中国-山西省-临汾市、长治市|临汾市
-> province=山西省，city=临汾市、长治市
```

截至 2026-07-24，加入独立招标计划项目后，928 个项目的预计结果：

| 提取结果 | 项目数 | 写入方式 |
|---|---:|---|
| 省市成功提取 | 923 | `province=山西省`，`city=首个有效分段中的一个或多个地级市` |
| 只能确认省份 | 2 | `province=山西省`、`city=NULL`，保留原地点并进入异常报告 |
| 省市均无法确认 | 3 | `province=NULL`、`city=NULL`，保留原地点并进入异常报告 |

原先32个地点为空的记录实际是招标编号被误当成项目编号后产生的重复项目；重新通过招标编号关联真实`E...`项目编号后，已全部取得对应招标公告中的省市。

### 4.2 公告字段权威顺序

项目静态字段通常按以下来源顺序选值：

```text
正常招标公告
> 资格预审公告
> 招标计划
> 中标候选人公示
> 中标结果公示
> 更正/终止类公告
```

延期、变更、补充、终止、暂停、控制价等公告不能用其带业务后缀的名称覆盖正式项目名称。

## 5. current_status 可写入的类型

当前实现支持 11 种状态。

### 5.1 正常生命周期状态

| current_status | 中文含义 | 判定标准 |
|---|---|---|
| `PLAN` | 招标计划 | 只有招标计划，且尚未按项目名称匹配到正式招标项目 |
| `PREQUALIFICATION` | 资格预审 | 有资格预审公告，但没有招标、候选人、中标或合同公告 |
| `TENDER` | 招标中 | 有招标公告，没有更高阶段公告，且最新递交截止/开标时间未到或无法取得 |
| `EVALUATING` | 已截止/评标中 | 没有候选人或更高阶段公告，并且最新递交截止时间或开标时间已经到达 |
| `CANDIDATE` | 中标候选人公示 | 至少有一条中标候选人公示，但没有定标候选人、中标结果或合同公告 |
| `FINAL_CANDIDATE` | 定标候选人公示 | 至少有一条定标候选人公示，但没有中标结果或合同公告 |
| `AWARD` | 中标结果 | 至少有一条中标结果公示，但没有合同公告 |
| `CONTRACT` | 合同履约 | 至少有一条合同与履约公告 |

### 5.2 异常流程状态

| current_status | 中文含义 | 判定标准 |
|---|---|---|
| `SUSPENDED` | 暂停 | 最新有效的整项目公告明确为暂停，并且之后没有恢复或更高阶段公告 |
| `TERMINATED` | 终止 | 最新有效的整项目公告明确为终止，并且之后没有恢复或更高阶段公告 |
| `CANCELLED` | 撤销 | 最新有效的整项目公告明确为撤销，并且之后没有恢复或更高阶段公告 |

“更正公告”不是项目生命周期阶段，因此没有 `CORRECTION` 项目状态。

## 6. current_status 判定优先级

### 6.1 总体流程

```text
最新整项目暂停/终止/撤销，且之后无正常进展
    ↓ 否
合同与履约公告
    ↓ 无
中标结果公示
    ↓ 无
定标候选人公示
    ↓ 无
中标候选人公示
    ↓ 无
最新递交截止时间/开标时间是否已经到达
    ├─ 是：EVALUATING
    └─ 否：TENDER
```

更完整的伪代码：

```text
如果最新整项目异常公告晚于最后一条正常进展公告：
    撤销 -> CANCELLED
    暂停 -> SUSPENDED
    终止 -> TERMINATED
否则如果存在合同公告：
    -> CONTRACT
否则如果存在中标结果：
    -> AWARD
否则如果存在定标候选人：
    -> FINAL_CANDIDATE
否则如果存在中标候选人：
    -> CANDIDATE
否则如果最新递交截止时间或开标时间 <= 当前时间：
    -> EVALUATING
否则如果存在招标公告：
    -> TENDER
否则如果存在资格预审公告：
    -> PREQUALIFICATION
否则：
    -> PLAN
```

### 6.2 招标公告和中标结果同时存在

```text
招标公告 + 中标结果公示
-> AWARD
```

中标结果是比招标公告更高的生命周期阶段，不能继续保存为 `TENDER`。

### 6.3 招标公告已经截止但没有候选人公告

```text
有招标公告
+ 当前时间已经超过递交截止时间或开标时间
+ 没有候选人/中标结果
-> EVALUATING
```

`EVALUATING` 是时间驱动状态。即使没有新公告，当前时间越过截止点后，也需要重新计算项目状态。

### 6.4 标段终止不能覆盖整项目

以下公告只表示标段级异常：

```text
某项目(001标段)终止公告
某项目(002,003标段)撤销公告
```

如果同一项目编号下其他标段仍有候选人或中标结果，项目整体不能直接标记为 `TERMINATED` 或 `CANCELLED`。

当前实现通过标题中的数字标段/包标识判断标段范围：

- 带明确数字标段或包：不覆盖整个项目状态；
- 不带标段且明确终止/撤销/暂停：可以作为整项目异常状态；
- 同一项目既有标段终止又有其他标段中标：项目保持最高正常生命周期阶段。

长期建议增加 `project_lot` 或 `project_section` 表，分别保存标段状态。

## 8. 递交截止时间与开标时间

### 8.1 现有覆盖情况

1,359 条招标公告中：

| 字段 | 有值公告数 | 覆盖率 |
|---|---:|---:|
| `递交截止时间` | 1,303 | 95.88% |
| `开标时间` | 1,303 | 95.88% |

当前 1,303 条公告的两个时间在忽略毫秒后相同，但仍应作为两个业务字段处理：

- 递交截止时间：最后允许提交投标文件的时间；
- 开标时间：开始开启或解密投标文件的时间。

### 8.2 Project 表的结构缺口

`project` 当前只有 `bid_open_time`，没有投标文件递交截止时间字段。

建议后续增加：

```prisma
bidSubmissionDeadline DateTime? @map("bid_submission_deadline")
```

在增加字段前：

- `递交截止时间`继续保留在 `notice_extraction.extracted_fields`；
- `current_status` 计算会使用`递交截止时间`；
- `project.bid_open_time`只写入开标时间；
- 不把递交截止时间错误写入 `bid_open_time`。

### 8.3 同项目多次延期

同一项目出现多个递交截止/开标时间时，项目摘要采用最新有效时间。每次公告原始时间仍保留在公告及抽取数据中。

项目状态计算使用：

```text
max(全部有效递交截止时间, 全部有效开标时间)
```

如果该最新时间已经到达，且没有候选人或更高阶段公告，则状态为 `EVALUATING`。

## 9. 状态更新时间要求

`current_status` 同时受公告事件和当前时间影响：

- 新公告入库后必须重新计算；
- `TENDER` 项目越过递交截止时间后，即使没有新公告也应变为 `EVALUATING`；
- 建议调度系统每天重新计算仍处于 `TENDER` 的项目；
- 已进入 `CANDIDATE`、`AWARD`、`CONTRACT` 的项目主要由新公告推进；
- 终止、撤销、暂停状态需要检查是否存在后续恢复或重新招标公告。

## 10. 写入说明

项目导入脚本执行：

```bash
npm run import:projects -- --commit --replace
```

将按照本文规则重新计算并写入 `current_status`。不带 `--commit` 时只预演，不修改数据库：

```bash
npm run import:projects -- --replace
```

使用`--commit --replace`时，脚本会在确认所有项目子表为空后删除旧项目，并为新项目显式写入连续的`id=1..928`；事务提交后将下一次`AUTO_INCREMENT`设置为929。因此本批项目主键从1开始，而不是沿用之前删除数据留下的两千多号自增值。

如果数据库已经写入`project_notice`，需要先清除公告及`notice_extraction.project_notice_id`关联，再重建项目和公告：

```bash
npm run import:project-notices -- --commit --replace --clear-only
npm run import:projects -- --commit --replace
npm run import:project-notices -- --commit --replace
```

`--clear-only`会先检查公告附件、项目要求、企业关系和合同等下游引用；存在引用时拒绝清除。
