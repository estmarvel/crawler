# 五站爬虫详细实现说明

本文对应当前 `Crawler_Scrapy` 实现，说明山西焦煤、山西省公共资源交易平台、
比比网、华新阳光采购平台和玖邦招标采购平台分别爬取什么、如何请求、怎样提取字段，
以及公告、快照、附件、断点和防封保护之间的关系。

## 1. 适用范围

| 站点 | Spider | 正式入口 | 默认栏目 |
| --- | --- | --- | --- |
| 山西焦煤电子招采平台 | `sxjm` | `./run_sxjm.sh` | 四个项目频道下的16个有效栏目 |
| 山西省公共资源交易平台 | `sxzwfw` | `./run_sxzwfw.sh` | 工程建设六类信息 |
| 比比网电子招投标交易平台 | `bitbid` | `./run_bitbid.sh` | 计划、招标、候选人、结果 |
| 华新阳光采购平台 | `huaxin` | `./run_huaxin.sh` | 招标/资审、候选人、结果、计划 |
| 玖邦招标采购电子交易平台 | `jiubang` | `./run_jiubang.sh` | 招标/资审、候选人、结果、计划 |

这些入口只采集公开公告，不登录用户账号，不写数据库。结果统一写入
`new_output/<site>/`，后续是否导入数据库由独立导入程序决定。

## 2. 统一采集流程

五个入口共用 `crawler_scrapy.site_runner`，一次完整运行分为两个阶段：

1. 公告阶段请求列表和详情，解析业务字段，保存正文、原始响应、HTML快照、附件清单、
   JSON、CSV和去重状态。
2. 附件阶段读取已经导出的JSON，根据公告ID逐个下载附件，再把文件路径、哈希、大小、
   类型和状态回写到同一条JSON及CSV记录。

公告和附件分离后，大文件下载不会占用Scrapy详情请求并发；公告已经保存后，即使附件
源站暂时不可用，也不会丢失公告正文和字段。

简化的数据流如下：

```text
公开列表/API
  -> 时间窗口、栏目和去重过滤
  -> 公开详情/API或服务端HTML
  -> 站点规则解析器
  -> 公共Notice Schema规范化
  -> HTML快照 + JSON/CSV + _trace
  -> 独立附件下载器
  -> 回写附件元数据
```

## 3. 公共字段模型

### 3.1 公告类型

公共框架预设八类字段结构：

- 招标计划 `PLAN`
- 资格预审公告 `PREQUALIFICATION`
- 招标公告 `TENDER`
- 中标候选人公示 `CANDIDATE`
- 定标候选人公示 `FINAL_CANDIDATE`
- 中标结果公示 `AWARD`
- 更正结果公示 `CORRECTION`
- 合同与履约 `CONTRACT`

本批五站实际主要覆盖计划、资格预审、招标、候选人、结果和更正。终止、废标、流标、
撤销等公告复用最接近的业务字段形状，但顶层公告类型编码保存为 `TERMINATION`。
源站栏目保存在 `公告子类型` 和溯源元数据中，不会因为复用公共Schema而丢失。

### 3.2 主要业务字段

所有已接入类型都预设独立的 `项目编号` 和 `招标编号`。编号只从明确的接口字段或正文
标签中提取；源站未提供时保存空值，不把同一个无标签编号复制到两个字段。后续项目关联
建议依次使用：项目编号、招标编号、项目名称。

各类核心字段如下：

- 招标计划：项目性质、招标方式、项目名称、项目编号、招标编号、项目类型、项目总投资、
  招标内容、招标人名称、行政监督部门、建设地点、建设内容及规模、预计发布时间、
  发布日期、发布网站。
- 资格预审/招标公告：项目名称、两个独立编号、行业、组织形式、开标时间、原组合编号、
  项目类型、投资/估算金额、招标金额、资金来源、地点、招标人/采购人、规模或概况、
  工期、质量、招标范围、资格要求、文件获取、递交、开启、评审、保证金和双方联系方式。
- 中标候选人：项目名称、两个独立编号、行业、组织形式、开标和公示时间、候选人名称、
  候选报价、招标人/采购人及代理机构联系方式。
- 中标结果：项目名称、两个独立编号、行业、组织形式、招标方式、中标人、联合体成员、
  中标价、工期、项目经理及证书、双方联系方式、依据文件和文号。
- 更正结果：项目名称、两个独立编号、所属行业、组织形式、开标和标书发售时间、更正
  内容、招标人、代理机构、监督部门联系方式及依据文件。

金额字段会按数据库类型进行规范化。例如正文中的“90.89万元”可转换为
`908900.00`；无法无损转换的费率、组合报价或带条件报价保留原文。候选人和报价先构造
逐条明细再拆成两个等长数组，避免价格错位。

### 3.3 公共存储字段

每条公告还包含：公告正文、解析状态、内容指纹、抽取方式、抽取版本、是否已核验、
爬虫时间、详情页链接、HTML快照路径、HTML快照SHA256和附件列表。

JSON额外保存 `_trace`，主要内容包括：

- 列表原始记录和详情原始payload；
- 请求参数、页码、总数、业务返回码和HTTP响应元数据；
- `rawHtml`、`rawText`；
- 快照路径、附件清单、缺失字段；
- 原文和快照的SHA256完整性信息。

CSV不重复保存 `_trace`，用于表格查看；JSON和快照才是完整溯源载体。

## 4. SXJM：山西焦煤电子招采平台

### 4.1 爬取范围

SXJM按首页真实频道和公告类型编码展开请求：

| 频道参数 | category | 栏目参数 | announcement_type | 源站类型 |
| --- | ---: | --- | ---: | --- |
| `yfxm` | 1 | `zbjh` | 19 | 招标计划 |
| `yfxm` | 1 | `zbgg` | 8 | 招标（预审）及其他公告 |
| `yfxm` | 1 | `hxr` | 2 | 中标候选人公示 |
| `yfxm` | 1 | `zbjg` | 10 | 结果公告 |
| `yfxm` | 1 | `zzgg` | 4 | 终止公告 |
| `zbxm` | 3 | `zbgg,hxr,zbjg,zzgg` | 1,2,3,4 | 招标项目四类公告 |
| `fzxm` | 2 | `cggg,cjhxr,cjgg,zzgg` | 5,6,7,4 | 非招采购、候选、成交、终止 |
| `jycg` | 4 | `cggg,zzgg,cjgg` | 5,4,7 | 限额以下采购、终止、成交 |

采购公告映射到招标公告字段，成交候选人映射到中标候选人字段，成交公告映射到中标结果
字段；`notice_subtype` 仍保留 `fzxm.cjhxr`、`fzxm.cjgg` 等真实类型。

### 4.2 请求过程

1. GET `/api/portal/v1/announcement/index`，提交频道、公告类型、页码和每页数量。
2. 使用与网站前端一致的AES-128-CBC参数解密响应中的 `result`。
3. 按发布时间窗口、公告ID、列表指纹和每个feed的数量限制筛选。
4. GET `/api/portal/v1/announcement/details/<公告ID>` 请求详情并解密。
5. 合并列表和详情，但原始两部分在独立 payload 快照中分开保存。

### 4.3 字段和附件

解析器优先使用详情结构化字段，再从 `content` HTML补充项目编号、招标编号、范围、
资格条件、时间、候选人、中标人、价格和联系方式。普通、再次、延期、变更、控制价、
终止等性质按接口编码与标题共同判断。

详情 `content` 原样保存为HTML快照；附件从详情文件数组生成清单。附件阶段按公告ID保存，
不会因同名文件覆盖其他公告。

## 5. SXZWFW：山西省公共资源交易平台

### 5.1 爬取范围

默认采集工程建设六个栏目：

| 参数 | channelId | 源站栏目 |
| --- | ---: | --- |
| `zbjh` | 198 | 招标计划 |
| `zbgg_zys` | 12 | 招标/资审公告 |
| `bg` | 13 | 更正公告 |
| `hxr` | 14 | 中标候选人公示 |
| `gs` | 15 | 中标结果公示 |
| `qt` | 16 | 其他公告 |

可选的政府采购栏目为 `zc_gz`（channelId 19，更正公告）和 `zc_jg`
（channelId 20，中标结果）。采购公告channelId 18尚未正式接入。

### 5.2 请求过程

1. 按前端真实表单POST `/queryContent-jyxx.jspx`；第二页开始请求
   `/queryContent_2-jyxx.jspx` 等分页地址。
2. 表单包含 `title`、`channelId`、起止日期、交易场所和项目类型。
3. 历史范围按自然月拆分，并优先处理最新月份，避免单个查询窗口页数过大。
4. 从服务端列表HTML读取公告ID、标题、日期、交易场所和 `.jhtml` 详情地址。
5. 详情直接请求服务端HTML，不使用浏览器渲染，不臆造JSON接口。

### 5.3 HTML还原和字段提取

普通富文本按块级标签保留换行。PDF转换页面会把视觉上的一行拆成多个绝对定位span，
解析器根据坐标重新拼行，并删除隐藏元素、签名和盖章占位。

公告类型优先按标题判断，无法判断时再用栏目兜底。项目名称、编号、金额、资金来源、
时间、范围、资格条件和联系方式均按正文明确标签提取。候选人和中标结果按明细行配对，
缺少报价时保留空值，不让后续价格前移。终止、废标、流标、撤销和有效投标人不足等
保存为终止类。

### 5.4 附件

正文中的直接链接进入附件清单。页面使用 `Cms.attachment(...)` 时，Spider先请求
`/attachment_url.jspx` 取得真实文件信息，再构造 `/attachment.jspx` 下载地址。
元数据请求失败会记录状态，公告本身仍正常导出。

## 6. Bitbid：比比网

### 6.1 爬取范围和接口

| 参数 | ggType | 详情接口 | 公共类型 |
| --- | ---: | --- | --- |
| `plan` | 4 | `/api/home/zbjhInfo/<id>` | 招标计划 |
| `tender` | 1 | `/api/home/ggInfo/<id>` | 招标公告 |
| `candidate` | 2 | `/api/home/hxrInfo/<id>` | 中标候选人公示 |
| `award` | 3 | `/api/home/zbjgInfo/<id>` | 中标结果公示 |

列表请求 `/api/home/bbzbMoreList`，参数包含页码、页大小、`ggType`、日期、地区和关键词。
`timeType=1` 用于保持与前端一致的最新优先顺序。

### 6.2 提取逻辑

招标计划主要使用 `zbjhInfo` 结构化字段。其他三类同时使用详情对象和HTML正文：

- `招标项目编号` 优先作为项目编号；`招标编号/采购编号/代理编号` 作为招标编号；
- 中文年月日时分转换为数据库时间；
- 支持招标人、采购人、建设单位、招标代理、采购代理和项目联系人模板；
- 招标公告解析范围、采购需求、资格、文件获取、递交、开启和保证金；
- 候选人按标段分组，支持数字、万元、百分比及组合费率报价；
- 结果公告提取中标人和价格，万元金额换算为元；
- 结果栏目内的废标、流标、终止、撤销公告保存为 `TERMINATION`。

统一运行器在公告阶段传入 `parse_pdf=false`，只使用API和HTML，PDF留给独立附件阶段，
避免大文件拖慢公告采集。

### 6.3 当前附件限制

比比网签章PDF位于 `zb.bitbid.cn`。当前服务器直连HTTP返回403，HTTPS还存在证书域名
不匹配。附件下载器遇到403/429会立即停止，不会反复请求或绕过源站限制。因此目前推荐
先运行 `--phase notices`；公告API中的正文足以保存和提取已验证的四类字段。

## 7. Huaxin：华新阳光采购平台

### 7.1 爬取范围

| 参数 | annClassifications | 源站栏目 | 可能输出类型 |
| --- | ---: | --- | --- |
| `zbgg_zys` | 1 | 招标/资审公告 | 资格预审或招标公告 |
| `hxr` | 2 | 候选人公示 | 中标候选人公示 |
| `gs` | 3 | 结果公示 | 中标结果或更正结果 |
| `zbjh` | 4 | 招标计划 | 招标计划 |

### 7.2 请求过程

华新是公开JSON API，不需要登录Token：

1. 普通公告POST `/bidding/bidAnnouncement/getWebAnnPage`；招标计划POST
   `/bidding/web/biddingPlan/biddingPlanList`。
2. 普通详情GET `/bidding/bidAnnouncement/getAnnWebByAnnId?annId=...`；没有数据时回退
   `/bidding/web/inputAnnouncement/getInputAnn?annId=...`。
3. 招标计划详情GET `/bidding/web/biddingPlan/getBiddingPlan/<id>`。
4. 列表和详情都再次检查发布时间，防止列表时间缺失或置顶旧公告造成越界。

### 7.3 字段和附件

解析器合并结构化字段、`annContent/annContent2`、项目概况、资格条件、获取/递交方式、
评审情况和联系方式等片段，并去除重复正文。`announcementType`、`annClassification`、
`annNature` 与标题共同决定资格预审、招标、候选、结果或更正类型。

候选人和中标结果优先读取结构化明细数组，缺失时回退正文规则。附件先从详情取得
`fileId`，再请求 `/bidding/file/query/<fileId>` 解析实际URL、文件名和大小；真正文件在
第二阶段下载。

## 8. Jiubang：玖邦招标采购电子交易平台

玖邦与华新使用同版本TWS招投标前端，栏目、列表结构、详情字段、`annNature` 和附件
`fileId` 语义一致，因此复用华新Spider流程和字段规则，但平台域名、接口地址、平台代码、
详情页链接和输出目录完全独立。

列表和详情过程为：

1. POST `https://www.bjjbkj.cn:9998/bidding/...` 的公告或招标计划列表；
2. 按 `annId` 或招标计划数值ID请求详情；
3. 必要时使用玖邦备用详情接口；
4. 使用 `JiubangParser` 调用经过实样修正的TWS公共字段规则；
5. 按玖邦平台代码保存JSON、CSV、快照、附件和状态。

当前只接入招投标模块四个一级栏目，不包括独立采购、竞价和零散采购模块。

## 9. 防封和出口保护

五站正式入口默认使用服务器直连，默认参数为：

- 总并发和单域名并发均为2；
- 每一批从3到5秒随机选择固定请求间隔；
- 开启AutoThrottle，源站响应变慢时自动进一步降速；
- 每400个响应主动结束当前Scrapy批次；
- 批次之间冷却180到300秒；
- 403或429第一次出现即主动停止；
- 直连时关闭系统环境代理继承；
- 普通失败只重试1次，避免高频重放。

这些设置降低固定IP被限流的概率，但不能保证源站策略永远不变。明确被拒绝后程序不会
自动切换身份或绕过限制。固定代理仅作为人工选择的备用模式。

## 10. 断点续爬和去重

运行范围由站点、日期、栏目、频道、页大小和数量限制共同计算哈希。相同范围使用同一个：

- Scrapy `JOBDIR`；
- 公告内容版本索引；
- 批次计数和完成标记；
- 站点级运行锁。

手动按Ctrl-C时，入口先向Scrapy转发SIGINT，已经写入的JSON、CSV、快照和去重记录保留。
下次执行完全相同的命令时，已经成功导出的详情不会重复抓取，未完成请求仍可恢复。

常用控制参数：

- `--refresh-notices`：完成标记存在时重新扫描列表，但仍按公告索引去重；
- `--check-updates`：重新检查已有公告是否发生正文变化；
- `--phase notices`：只抓公告和附件清单；
- `--phase attachments`：只下载已有JSON中的附件；
- 默认 `--phase all`：公告完成后再运行附件。

附件文件使用确定性路径。完整文件直接跳过；中断留下 `.part`，下次优先使用HTTP Range
续传。默认连接超时30秒、流读取超时900秒、重试4次；403/429直接终止而不是重试。

## 11. 输出目录

```text
new_output/<site>/
├── json/          # 完整公告和_trace
├── csv/           # 固定表头的业务结果
├── snapshots/     # HTML原文快照
├── payloads/      # 列表/详情原始载荷快照
├── attachments/   # 附件二进制
├── logs/          # 每批公告和附件日志
└── state/         # JOBDIR、去重、锁、批次和完成标记
```

没有HTML正文的结构化招标计划可能没有独立HTML快照，但原始详情 payload 仍完整保存在
`payloads/` 中，并由 `_trace.payloadSnapshot` 定位和校验，可用于回溯。

## 12. 运行命令

先进入项目目录：

```bash
cd /home/intsig/Crawler_Scrapy
```

最近180天，公告完成后下载附件：

```bash
./run_sxjm.sh
./run_sxzwfw.sh
./run_huaxin.sh
./run_jiubang.sh
```

比比网当前建议只抓公告：

```bash
./run_bitbid.sh --phase notices
```

指定栏目和日期：

```bash
./run_sxzwfw.sh --phase notices \
  --sections zbgg_zys,hxr,gs \
  --start-date 2026-07-01 --end-date 2026-08-05
```

每种栏目最多5条，用于规则抽样：

```bash
./run_bitbid.sh --phase notices \
  --sections plan,tender,candidate,award \
  --max-records 5 --max-pages 3 --page-size 20
```

全历史：

```bash
./run_sxjm.sh --all-history
./run_huaxin.sh --all-history
```

SXZWFW的 `--all-history` 当前定义为2020-01-01至运行当天，因为该站列表接口必须提交
起止日期。其他四站全历史模式不提交开始日期。

只下载附件并放宽大文件读取超时：

```bash
./run_huaxin.sh --phase attachments \
  --attachment-connect-timeout 60 \
  --attachment-read-timeout 1200 \
  --attachment-retries 5
```

查看全部配置：

```bash
./run_sxjm.sh --help
./run_sxzwfw.sh --help
./run_bitbid.sh --help
./run_huaxin.sh --help
./run_jiubang.sh --help
```

发生问题时按以下顺序检查：

1. `logs/` 中的HTTP状态、结束原因和业务返回码；
2. JSON顶层 `解析状态`、`缺失字段` 和附件 `parse_status`；
3. `_trace.responseMetadata` 与 `_trace.payloadSnapshot`；
4. 顶层正文、HTML 快照和 payload 快照是否存在；
5. `HTML快照SHA256`、payload 快照 SHA256 与实际文件是否一致；
6. `state/` 中是否存在同范围完成标记或运行锁。

字段为空不一定代表解析失败。只有当原始正文或payload明确存在该字段，而规则结果为空或
错位时，才应修改解析器；源站本身没有提供的字段必须保持空值。
