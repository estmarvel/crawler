# 爬虫运行问题分类与前后端任务接入更新说明

更新时间：2026-08-25

适用范围：`/home/intsig/Crawler_Scrapy` 当前 Scrapy 框架，以及后续将该框架接入采集中心前后端时的任务启动、停止、续跑、进度和异常处理。

## 1. 结论

本次发现的问题不是单一原因，可分为四类：

1. **爬虫/框架逻辑问题**：导出器公共方法缺失、AI 服务异常状态未初始化、列表请求错误绕过去重、异常附件 URL 未标准化。这些问题必须修改 `Crawler_Scrapy` 代码，单纯重启任务不能根治。
2. **任务运行器问题**：停止时重复发送中断信号，可能破坏 Scrapy 的持久化 JOBDIR。这属于运行器生命周期管理问题，不是字段解析问题。
3. **任务参数问题**：公告和附件虽然已经分阶段，但公告仍使用 300 秒超时，导致源站悬挂时长时间占用并发槽。这应由统一任务入口设置合理参数。
4. **修复前遗留状态**：比比网、SXJM 已经积累的重复请求队列，以及一次中断产生的空队列头文件。这些不是新代码继续产生的问题，需要保留去重数据并让旧队列收敛，或在备份后修复损坏文件。

前端不负责网站请求、HTML/PDF 解析、字段规则或 AI 决策。后端也不应复制这些逻辑；后端只负责调用统一爬虫入口、传递经过校验的参数、管理进程、记录任务和推送进度。

## 2. 问题归属与处理结果

| 问题 | 归属 | 表现 | 根因 | 处理结果 |
| --- | --- | --- | --- | --- |
| `_write_formats` 不存在 | 通用爬虫框架逻辑 | 已请求详情但 JSON 写入失败，日志出现 `AttributeError` | 站点专用导出器依赖公共导出方法，但公共 Pipeline 未提供该方法 | 已在公共导出 Pipeline 补齐统一 JSON/可选 CSV 写入；当前全量任务关闭 CSV |
| `_fatal_error` 不存在 | 通用 AI 解析逻辑 | AI Pipeline 抛出 `AttributeError`，模型结果无法应用 | AI 服务异常状态未在所有构造路径初始化 | 已统一初始化并保留规则解析兜底；模型失败不再丢公告 |
| 比比网列表重复扫描 | 比比网站点爬虫逻辑 | 多个 400 响应批次长期零新增，JOBDIR 恢复请求数不断增加 | 列表首页及翻页设置 `dont_filter=True`，每次分批重启都会再插入一组完整翻页链 | 已让列表请求使用 Scrapy 持久化去重；详情更新和公告级去重逻辑保持不变 |
| SXJM 列表重复扫描 | SXJM 站点爬虫逻辑 | 每次重启增加约一组 feed 首页，历史请求队列由 544 增长到 576 | 列表请求同样错误绕过持久化去重 | 已只取消列表请求的 `dont_filter`；详情请求仍保留原有补采语义 |
| SXZWFW 嵌入 PDF 请求异常 | SXZWFW 解析逻辑 | 个别公告抛出 `Port could not be cast to integer`，整条公告可能无法完成 | 源页面使用 `http://host:port\upload\...pdf` 形式的 Windows 反斜杠路径 | 已先将反斜杠标准化为 `/`，再验证 scheme、hostname 和 port；坏附件只跳过，不再丢整条公告 |
| JOBDIR 队列头损坏 | 任务运行器逻辑及运行状态 | 启动时报 `struct.error: unpack requires a buffer of 4 bytes` | tmux 的 Ctrl-C 已同时到达父子进程，SiteRunner 又补发一次 SIGINT，Scrapy 将第二次信号视为强制退出，队列头来不及落盘 | 已修改 SiteRunner：先等待 Scrapy 对第一次信号优雅退出，超时后才逐级使用 SIGTERM/SIGKILL；损坏的比比网 JOBDIR 已先备份再修复 |
| 公告请求长时间假死 | 任务参数问题 | 两个并发槽同时等待源站，数分钟没有响应或新增 | 公告错误沿用附件场景的 300 秒超时 | 全量任务公告超时已改为 90 秒；附件连接超时仍为 30 秒、读取超时仍为 900 秒 |
| 比比网修复后暂时零新增 | 修复前遗留状态，不是新故障 | 响应数持续增长但 item 为 0 | 正在消费修复前已排入 JOBDIR 的重复历史列表，并由公告去重索引跳过 | 不清空 JSON、快照或去重索引，让遗留队列自然收敛；收敛后自动进入下一站 |
| `FormRequest is deprecated` | 兼容性警告 | 山西新点日志有 Warning，但仍持续写入 | Scrapy 新版本建议未来改用 `form2request` | 当前不是运行失败，不影响数据；可作为后续依赖升级任务处理，不应误报为采集失败 |

## 3. 哪些必须更新爬虫代码

以下修改属于爬虫自身，后端重试或修改超时无法替代：

- `crawler_scrapy/pipelines.py`：公共导出方法、JSON-only 配置。
- `crawler_scrapy/ai/html_extractor.py` 及公共 AI 服务：模型失败状态初始化与规则结果兜底。
- `crawler_scrapy/spiders/bitbid.py`：列表请求必须参与 JOBDIR 去重。
- `crawler_scrapy/spiders/sxjm.py`：列表请求必须参与 JOBDIR 去重，详情补采语义不变。
- `crawler_scrapy/sites/sxzwfw/parser.py`：附件地址标准化和合法性校验。
- `crawler_scrapy/site_runner.py`：安全停止和 JOBDIR 落盘保护。
- `run_ai_full_crawl.sh`：公告 90 秒、附件 900 秒的分阶段超时。

这些修改不会改变数据库结构，也不会改变八类公告 Schema。已经保存的 JSON、快照、payload、附件和公告级去重索引均继续兼容。

## 4. 后端接入原则

### 4.1 一条任务只运行一个网站

数据库中的一条 `crawl_task` 必须只对应一个 `data_source` 和一个 Spider。后端不要把 `run_ai_full_crawl.sh` 当作普通任务入口，因为该脚本是服务器运维用的多站顺序队列；中途重启整条队列时，会从队列中的第一个网站重新检查。

后端应调用以下任一单站入口：

```text
run_<site>.sh
  -> python -m crawler_scrapy.site_runner <site>
  -> scrapy crawl <site>
```

`run_ai_full_crawl.sh` 只用于人工全量运维，不直接绑定一个 `crawl_task.id`。

### 4.2 任务与输出目录隔离，去重状态共享

推荐保持已有设计：

- 本次任务 JSON、日志和运行结果写入任务独立目录，例如 `runtime/crawler-output/<taskId>/<site>/`。
- 站点公告身份和版本去重根目录使用稳定的全局目录，避免不同任务重复保存同一版本。
- JOBDIR 的任务作用域必须由“网站、时间范围、栏目、分页和 AI 配置”等稳定参数生成；相同参数重试复用同一作用域。
- 前端传入的任务名称、备注等展示字段不得参与 JOBDIR 哈希，否则只改名称也会失去断点。

### 4.3 公告和附件分阶段

后端按以下阶段运行：

```text
FETCH_NOTICES
  -> 保存 JSON、原始 HTML/API payload、正文快照和附件清单
DOWNLOAD_ATTACHMENTS
  -> 根据公告 ID + source_file_id 下载附件并回写状态
IMPORT
  -> 按现有幂等导入脚本写数据库
VERIFY
  -> 核对任务发现关系、快照、附件和数据库记录
```

公告和附件可以并行使用不同 worker，但同一附件只能有一个下载者；附件必须通过公告 ID 和 `source_file_id` 关联，不能靠文件名关联。

## 5. 后端启动参数要求

后端应使用白名单转换参数，不允许前端直接拼接 shell 命令。建议值如下：

| 参数 | 建议值 | 说明 |
| --- | --- | --- |
| `phase` | `notices` / `attachments` | 前后端展示为独立阶段 |
| `outputRoot` | 任务独立目录 | 不接受用户输入任意绝对路径 |
| `dedupRoot` | 服务端固定全局目录 | 不在前端展示或修改 |
| `responsesPerChunk` | 400 | 只表示单进程响应预算，不表示任务总量 |
| `concurrency` | 通常 2；站点可覆盖为 1 | 必须服从站点安全配置 |
| `delayMin/delayMax` | 3～5 秒 | 由后端配置，不开放任意零延迟 |
| `requestTimeoutSeconds` | 90 | 仅公告 HTML/API 请求 |
| `attachmentConnectTimeoutSeconds` | 30 | 附件阶段独立配置 |
| `attachmentReadTimeoutSeconds` | 900 | 大 PDF/压缩包不得沿用公告超时 |
| `aiModel` | `Qwen/Qwen3-8B` 或受支持模型 | 前端只能选择后端白名单 |
| `aiApiKeyEnv` | 服务端根据账号选择 | API key 只存在 `.env`，不能通过前端或命令行传递 |
| `aiMaxCalls` | 0 表示不设置任务次数上限 | 仍受提供方 RPM/TPM 和全局节流器约束 |

`crawl_task.run_config` 应保存去除密钥后的实际参数，便于重试复现。不得保存 API key 明文。

## 6. 后端安全停止逻辑

正确的停止过程：

1. 将任务状态改为 `CANCEL_REQUESTED`，阻止重复点击停止。
2. **只向受管进程组发送一次 SIGINT**，让 Scrapy 关闭下载器、Pipeline、请求队列和 `spider.state`。
3. 等待最多 `requestTimeoutSeconds + 30` 秒。公告默认可等待约 120 秒；附件应按附件读取超时单独判断。
4. 仍未退出时发送一次 SIGTERM，再等待 10 秒。
5. 最后才允许 SIGKILL，并把任务记录为异常停止；不能把这种情况显示为正常取消。
6. 进程退出后验证 JOBDIR：零字节 LIFO 队列头、无法反序列化的 `spider.state` 或缺失的完成标志需要记录为任务执行异常。

禁止以下做法：

- 父进程收到 Ctrl-C 后立即再次向 Scrapy 补发 SIGINT。
- 先杀 SiteRunner，再单独遗留 Scrapy 子进程。
- 删除整个 JOBDIR 来“解决”启动失败。
- 因单条附件失败回滚已保存公告。

当前不需要修改数据库结构。若数据库异常类型暂时没有专门的 JOBDIR 代码，可继续使用现有 `TASK_EXECUTION`，并在任务事件/错误详情中保存子代码 `JOBDIR_CORRUPTED`，前端按子代码显示中文原因。

## 7. 进度与健康状态判断

仅判断 PID、tmux 会话或 `RUNNING` 状态不足以证明爬虫健康。后端应同时采集：

- 当前网站和阶段；
- 当前 chunk；
- `response_received_count`；
- `item_scraped_count`；
- `dedup/known_identities_skipped`；
- `scheduler/enqueued`、`scheduler/dequeued` 和恢复请求数；
- 最近一次日志/响应/落盘时间；
- JSON、快照、附件累计数量；
- 最近的 HTTP 状态、AI 调用错误和异常堆栈。

状态判断规则：

| 现象 | 正确判断 |
| --- | --- |
| 响应持续增长、item 为 0、known skipped 增长 | 正在历史去重扫描，不直接判失败 |
| 响应和 item 都增长 | 正常采集 |
| 90 秒内无响应，随后出现一次下载超时并继续 | 可恢复的单请求超时 |
| 超过 240 秒无响应、无 AI 调用、无落盘且进程仍在 | 标记 `STALLED` 告警，后端进一步检查连接和日志 |
| 出现 `AttributeError`、`struct.error`、未捕获 `ValueError` | 代码或运行状态错误，不能仅靠自动重试掩盖 |
| `finish_reason=closespider_pagecount` | 只完成一个 chunk，应由 SiteRunner立即续跑，不能将数据库任务标记成功 |
| `finish_reason=finished` 且附件/导入阶段完成 | 才能进入最终成功校验 |

现有 `_ai_full_control/*.status` 只在阶段切换时更新，不是实时心跳。前后端不能只读取它的 `updated_at` 判断卡死；应优先使用 Scrapy logstats、SSE 日志和输出计数。

## 8. 前端需要更新的内容

前端不接收或实现爬虫规则，只做以下调整：

1. 任务列表展示“网站、阶段、chunk、响应数、新增数、去重跳过数、最近活动时间”。
2. 将“运行中但零新增”细分为“历史去重扫描”“等待源站响应”“附件下载中”，不要统一显示为异常。
3. 停止按钮点击后显示 `停止中`，等待后端确认进程退出；不能立即把本地状态改为 `已停止`。
4. 日志页通过 SSE 展示真实 Scrapy 日志，页面轮询只作为 SSE 断线后的补充。
5. 对 `TASK_EXECUTION/JOBDIR_CORRUPTED`、`ACCESS_BLOCKED`、`TASK_TIMEOUT` 等显示不同处理建议。
6. 重试按钮复制原任务参数但生成新任务 ID；续跑使用后端保存的 JOBDIR 作用域，前端不能提供“清空断点”快捷操作。
7. API key 只显示“账号槽位/是否配置”，不显示或回传密钥内容。

## 9. 后端异常分类建议

不改变现有数据库结构时，可继续使用已有异常类型，并在事件元数据或错误详情中增加应用层子代码：

| 现有异常类型 | 建议子代码 | 场景 |
| --- | --- | --- |
| `TASK_EXECUTION` | `SPIDER_LOGIC_ERROR` | 未捕获解析/导出/AI Pipeline 异常 |
| `TASK_EXECUTION` | `JOBDIR_CORRUPTED` | 队列头或 spider.state 无法读取 |
| `TASK_EXECUTION` | `TASK_STOP_FAILED` | 优雅停止超时后被强制终止 |
| `TASK_TIMEOUT` | `TASK_DEADLINE_EXCEEDED` | 整个任务超过用户配置的总时限 |
| `ACCESS_BLOCKED` | `HTTP_403_OR_429` | 防封中间件确认源站限制访问 |
| `OUTPUT_DIRECTORY_FAILED` | `OUTPUT_WRITE_FAILED` | JSON、快照或附件目录不可写/磁盘不足 |

单个 HTTP 请求达到 90 秒只计入 Scrapy 请求统计，不应直接创建一个 `TASK_TIMEOUT`；只有任务总时限达到后才使用该类型。

## 10. 上线更新顺序

1. 部署当前 `Crawler_Scrapy` 代码和依赖，不清空现有输出、去重索引或 JOBDIR。
2. 后端切换为单站 `site_runner` 入口，并实现单次 SIGINT 的停止流程。
3. 后端补充结构化进度采集及 SSE 字段，不修改数据库结构。
4. 前端增加阶段、响应、去重和最近活动展示。
5. 先选择一个小范围任务验证启动、停止、续跑、JSON、快照和附件。
6. 再做一次 400 响应分批测试，确认跨 chunk 不重复插入列表首页。
7. 最后恢复全量任务；比比网和 SXJM 的旧重复队列应允许自然收敛。

## 11. 验收标准

- 同一 JOBDIR 连续运行至少两个 chunk，恢复请求数不因启动首页而固定增长。
- 手动停止一次后 JOBDIR 可直接重开，不出现 `struct.error` 或空 `spider.state`。
- 公告源站悬挂时，单请求约 90 秒超时并释放并发槽；附件仍可持续读取至 900 秒。
- SXZWFW 的反斜杠 PDF 地址能够转为合法 URL；非法附件不会阻止公告 JSON 和快照落盘。
- AI 不可用或返回异常时保留规则结果并记录元数据，不丢公告。
- JSON-only 任务不生成 CSV，站点专用导出器正常写入 JSON。
- 前端停止状态与真实进程一致；数据库任务只在所有配置阶段完成后标记成功。
- 所有任务仍使用当前数据库结构，不执行 Prisma migration 或 DDL。

## 12. 当前验证结果

本次相关定向回归用例全部通过，覆盖：

- 比比网列表请求使用持久化去重；
- SXJM 列表请求使用持久化去重；
- SXZWFW 反斜杠嵌入 PDF 地址标准化；
- SiteRunner 单次中断与优雅退出；
- 站点专用导出器 JSON 写入。

运行观察中，山西新点持续新增；比比网正在消费修复前遗留请求；SXJM 已从长时间零写入恢复为可写入状态。历史日志中的旧异常不会被删除，后续判断应以修复时间之后的新 chunk 日志为准。
