## 2. 项目地点标准修正

旧规则把项目地点截断到区/县，会把“山西省文水中学校”错误变为“山西省”。
现规则改为保留源文明确的完整履约地点，可具体到学校、厂区、矿区、园区、
道路和乡村；模型仍必须用“项目地点、建设地点、实施地点、服务地点、供货
地点或交货地点”等角色标签举证，禁止把招标人地址、代理机构地址、文件递交
地址当成项目地点。

### 3.1 名称和报价对齐

SXJM 历史结果中候选人/中标人名称数组与空报价数组不等长，主要原因是源站
确实没有公布报价，并非名称提取错误。新规则保留名称数量，同时为每个未公布
价格写入同索引 `null`。这既满足可溯源性，也避免把“未公布”误判为“漏提取”。

## 4. 字段调用边界

### 4.1 永不交给模型推测的字段

- 发布网站、发布日期和源站公告类型；
- 已由可信 API 明确提供且在 `*TrustedFields` 中标记的值；
- 项目性质等确定性枚举映射；
- 快照路径、哈希、附件和其他溯源字段。

### 4.2 动态异常升级条件

以下任一条件成立时，才把对应主要业务字段及局部证据窗口交给模型：

1. 规则为空，但正文存在该字段的明确标签；
2. 规则结果残留 HTML 标签或 HTML 实体；
3. 长章节包含多个明显属于后续章节的标签；
4. 候选人/中标人名称与报价数量不一致；
5. 局部窗口抽取与规则发生实质冲突，需要扩大到完整相关章节复核。

模型结果必须回传窗口 ID 和原文行范围。程序会检查证据是否存在于正文、字段
标签和角色是否匹配、金额和日期类型是否合法、并行列表是否同源同范围。模型
不能仅凭置信度覆盖规则；有值冲突时需要候选窗口和扩大章节两阶段结果一致。

## 5. 四站字段配置

- `sxjm`：项目/招标编号、地点、金额、资金来源、规模、范围、资格、质量、
  获取/递交方式及候选/中标名单等只在异常时升级。
- `bitbid`：同样以异常升级为主，重点处理 PDF/HTML 合并后的章节边界、HTML
  残留、编号污染及名单报价对应关系。
- `trade365`：`招标内容与范围`、`申请人资格要求/投标人资格要求`进行常规
  窗口复核；其余主要字段异常升级。
- `sxzwfw`：招标计划、资格预审、招标、候选、结果字段异常升级；`公告内容`
  和`合同主要内容`进行常规长章节边界复核。

## 6. 启用方式与默认行为

四个运行脚本现在都会从项目根目录 `.env` 加载 `ZHIPUAI_API_KEY`，密钥不写入
命令行和日志。AI 默认关闭；只有显式增加 `--ai-extract` 才会调用模型：

```bash
./run_sxjm.sh --phase notices --ai-extract
./run_bitbid.sh --phase notices --ai-extract
./run_trade365.sh --phase notices --ai-extract
./run_sxzwfw.sh --phase notices --ai-extract
```

四站的默认 AI 模型已统一为 `glm-5.2`。本次仅完成代码接入，未执行上述命令。
