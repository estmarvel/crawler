### 2.4 发现的问题

#### 已修复：玖邦候选人和报价漏提及二次表格误识别

5条中标候选人公示的正文均明确包含候选人和报价，但以下字段5/5为空：

- `中标候选人名称`
- `中标候选人报价`
- `中标候选人明细`

正文存在两种首轮规则没有覆盖的格式：

1. `第1名：某公司,投标报价：782000元`；
2. 纵向表格文本：`排序 / 中标候选人名称 / 投标报价（万元） / 1 / 公司 / 金额`。

测试时的回退规则主要识别“推荐中标候选人名称：”，因此没有命中。这是解析缺陷，
不是源站缺失。现已增加“第N名同一行”和纵向表格规则，并以
`中标候选人明细`成对保存。纵向表格现在会在第二个“序号”或“候选人响应/资格”
表前停止，且报价单元后只接受数值。第二批5条真实正文在最新规则下均正确；原测试
JSON/CSV作为历史结果不会被覆盖。

#### 已修复：联系方式边界不干净

15条普通公告中有10条至少一个联系方式字段混入下一个标签内容，例如：

- 地址字段包含`联 系 人`和`电 话`；
- 联系人字段包含电话号码；
- 部分正文已有联系人/电话，但结构化结果仍为空。

原因包括：玖邦常用`招 标 人`、`联 系 人`、`电 话`等带空格标签；独立联系方式HTML有时
只包含一方。最新规则仅对行首标签做空格规范化，将完整`annContent`作为主来源，
再用`bidContactInformation/contactInformation`补缺；并在下一个地址、联系人、联系电话等
标签前停止，避免字段相互吞入。

#### 已修复：公告正文重复段落

4条候选公示和2条结果公示出现整段或大段重复。API的`annContent`已经包含评标情况、
异议、监督和联系方式，解析器又把`reviewSituation`、`contactInformation`等结构化
片段拼接到正文。旧规则仅对完全相同的整段去重，无法去掉正文中的子段重复。

现在清洗后的结构化子段如果已完整包含在主正文中就不再追加，避免JSON体积、AI上下文和
关键词统计受重复内容影响。

#### 已修复：正文有值但部分招标公告字段漏提

本次5条招标公告中：

- `工期/服务期/供货日期`空4条，其中正文存在`交 货 期`、`计划工期`、`服务期限`；
- `获取方式`空3条，正文常以`2.获取方法`、`4.2获取方法`或带空格形式出现；
- `递交方法`空2条，正文实际存在递交方法；
- `资金来源`空2条，其中至少一条正文为“项目资金为企业自筹”；
- 某条`质量要求`把后续`交货地点`一起吞入；
- 联系方式字段存在上述漏提和污染。

主要原因是编号标签和带空格标签的正则边界覆盖不足。例如现有编号规则没有完整消费
`2.`的末尾点号，通用停止标签也没有覆盖`交货地点`。

最新规则又补充了“资金来源为”“服务期限”“招标代理”和无显式标签的下载句，并将
`招标内容与范围`按章节提取，在后续工期、质量、地点或资格章节前停止。两站最新40条
真实正文离线复验未再出现上述已知格式漏提。

#### 已修复：项目编号保存不完整及跨行粘连

多个招标公告正文同时存在交易项目编号和代理招标编号，例如：

- `E1401005107101357001`
- `ZDF03-HZ260502`

旧规则通常只保存E开头的交易编号；放宽代理编号后，又曾因删除全部换行而把下一小节
`2.3`的`2`粘到编号末尾。最新规则分别扫描API字段和正文，并只删除水平空格，既保留
两个不重复编号，也不会跨行消费下一小节编号。

#### 覆盖不足：本次没有验证四种预设类型

本次结果没有出现：资格预审公告、定标候选人公示、更正结果公示、合同与履约。
因此不能用本次成功率推断这四类已经可用。当前代码中，定标候选人和合同与履约还
没有 TWS 专用解析路径，属于明确的能力缺口。

## 5. 技术实现

### 5.1 代码复用结构

- `BaseNoticeSpider`：统一公告Item、内容指纹和列表阶段去重接口。
- `HuaxinSpider`：实现TWS列表、详情、备用详情、附件链路和出口策略。
- `JiubangSpider`：继承TWS流程，只覆盖玖邦配置、平台身份和解析器。
- `HuaxinParser`：实现共享字段规则、公告分类、联系人、中标明细和附件元数据。
- `JiubangParser`：继承共享规则，只覆盖平台名和用户详情页域名。
- `notice_fields.py`：定义8种公告的固定字段顺序、类型转换和数据库兼容类型。

对应文件：

| 模块 | 文件 |
|---|---|
| 华新站点配置 | `crawler_scrapy/sites/huaxin/config.py` |
| 华新/共享解析规则 | `crawler_scrapy/sites/huaxin/parser.py` |
| 华新及TWS请求流程 | `crawler_scrapy/spiders/huaxin.py` |
| 玖邦站点配置 | `crawler_scrapy/sites/jiubang/config.py` |
| 玖邦解析入口 | `crawler_scrapy/sites/jiubang/parser.py` |
| 玖邦Spider | `crawler_scrapy/spiders/jiubang.py` |
| 统一字段Schema | `crawler_scrapy/schemas/notice_fields.py` |
| 快照/附件/Schema/AI/导出 | `crawler_scrapy/pipelines.py` |
| 代理和失败关闭 | `crawler_scrapy/transport/proxy_middleware.py` |
| 跨运行去重 | `crawler_scrapy/storage/dedup.py` |
| 双站历史采集入口 | `run_tws_history.sh` |

这种方式避免两个同系统网站各复制一份解析器。后续修复候选人、联系方式等规则时，
需要用华新和玖邦样本同时做回归测试，防止修复玖邦格式后破坏华新格式。

### 5.2 单条公告处理流程

1. 按栏目发送列表POST请求。
2. 读取`records`、`total`和`pages`，按发布日期过滤；到达起始日期或源站最后一页即停止。
3. 使用平台代码和公告ID检查跨运行索引；严格模式下已保存ID不再请求详情。
4. 普通公告请求主详情API，无数据或失败时请求备用详情API；招标计划请求计划详情。
5. 用列表数据补齐详情对象缺失值，但不覆盖详情已有值。
6. 根据栏目、`annClassification`、`annNature`、`announcementType`和标题识别Schema。
7. 优先读取结构化API字段，再用正文规则补充；联系人以正文为主、API为补充。
8. 若存在`fileId`，请求文件服务解析预览/下载URL，然后由文件Pipeline下载原件。
9. 按统一Schema补齐字段、转换日期/金额/list/dict类型并记录缺失字段。
10. 可选AI仅补规则仍为空的业务字段；当前默认关闭。
11. 按公告身份和内容指纹过滤重复版本。
12. 追加写入固定JSON/CSV，更新去重索引，不覆盖历史版本。

### 5.3 Pipeline顺序

1. `NoticeDedupPipeline`：过滤相同公告的相同内容版本。
2. `HtmlSnapshotPipeline`：公共能力；华新和玖邦目前均显式关闭快照。
3. `NoticeFilesPipeline`：下载附件并写回路径、哈希、大小和MIME类型。
4. `NoticeSchemaPipeline`：字段规范化、类型转换和缺失字段统计。
5. `AiHtmlExtractionPipeline`：默认关闭，只补空字段且不覆盖规则值。
6. `NoticeMultiFormatPipeline`：追加写入JSON与CSV。

## 6. 代理、限速和反封禁方案

两个Spider默认使用固定认证代理，`direct`模式会在初始化时直接报错。代理凭据缺失、
407认证失败、代理网络异常且重试耗尽时关闭Spider，不会回退服务器真实IP。列表、
详情、文件元数据和附件下载请求都经过固定代理。

当前保守参数：

- 总并发2、单域名并发1；
- 基础延迟3秒并随机化；
- AutoThrottle目标并发0.5，最大延迟60秒；
- 网络重试1次；
- 403/429时提高下载槽延迟，连续2次或累计4次主动结束；
- 单次最多接收300个响应；
- 测试脚本最多运行20分钟。

天启代理池仍作为备用，配置为3分钟、每次10个、测试最多调用1次、生产默认最多5次，
无可用代理立即终止。当前临时固定代理账号密码明文存在测试脚本中，这是用户确认的
临时方案；生产运行前应迁移到环境变量或密钥服务，并删除脚本明文。

## 7. 去重和保存方案

每个平台使用独立目录：

```text
output/<platform>/json/
output/<platform>/csv/
output/<platform>/attachments/
output/<platform>/state/notice_versions.json
output/<platform>/<platform>.log
```

公告身份优先使用`平台代码+公告ID`；内容版本使用正文、HTML或结构化数据的SHA256。
同一ID正文改变时会追加新版本，旧记录保留；同一ID同一内容不会重复追加。测试脚本
启用严格已知ID跳过，可避免重复请求详情，但也不会发现已保存公告后续被源站修改。

CSV使用追加行；JSON维持标准数组格式，在结束符前追加对象。两个文件格式记录数已在
玖邦本次测试中核对一致。

本次玖邦审计使用的实际结果位于：

- `output/jiubang/json/`
- `output/jiubang/csv/`
- `output/jiubang/attachments/`
- `output/jiubang/jiubang.log`

## 8. 八种预设类型的字段可获得性

这里区分三种情况：源站通常不提供、当前规则未实现、正文存在但规则漏提。

### 8.1 招标计划

已实现且玖邦5条验证成功。API可直接提供招标方式、名称、类型、总投资、内容、招标人、
监督部门、地点、规模、预计发布时间和发布日期。

当前稳定为空：

- `项目性质`：计划API没有对应明确值，按约定不推断；玖邦5/5为空。
- `公告正文`：计划是结构化详情，没有普通公告HTML正文，当前为空是设计结果。
- HTML快照字段：站点关闭快照，保持空值。

### 8.2 资格预审公告

分类与Schema已实现，但本次玖邦没有样本，不能确认真实提取率。通常可能缺失：

- `项目性质`、`项目总投资/估算金额`、`招标金额`；
- `评审办法`、`投标保证金方式`、`开启地点`；
- 招标人/代理机构地址、联系人、联系方式中的部分字段。

带编号、带空格标签仍可能导致获取方式、递交方法、联系人等正文值漏提。

## 9. AI提取的定位

AI接口已经统一封装，但默认关闭，本次20条均为`jiubang-rule-parser`结果，没有调用
模型。启用后只把规则仍为空且由Spider允许的字段提交给模型，不覆盖已有规则值。

AI适合处理低频、格式差异大的正文字段，不应代替以下确定性修复：

- “第1名”候选人和报价配对；
- 纵向候选人表格解析；
- 带空格的联系人标签边界；
- 项目编号正则；
- 正文重复段落去重。

这些问题应先用规则解决，之后再让AI补充真正非结构化或少见字段，以控制费用和保持
结果可复现。

## 10. 批量爬取方案和当前限制

### 10.1 当前可用方式

当前Spider支持按栏目配置`max_records`、`page_size`和`max_pages`，适合小批次验证或
从最新数据向后分页。状态索引允许重复运行并跳过已经保存的公告。

### 10.2 六个月历史数据建议

生产采集应按时间窗口分批，而不是一次无限翻页：

1. 普通公告增加`start_time/end_time`参数，传入列表API的发布时间条件；
2. 建议按月或按周分片，四个栏目分别运行；
3. 每个分片保存页码、时间边界、请求数、成功数和失败ID；
4. 首轮采集关闭“已知ID绝对跳过”或使用列表指纹，以允许公告更新形成新版本；
5. 附件失败单独重试，不重复抓取整条公告；
6. 每批完成后检查类型计数、关键字段空值率和异常状态再进入下一批；
7. 保持单域名并发1和3秒以上随机延迟，根据403/429情况进一步降速。

当前代码还没有对外提供开始/结束时间参数，默认`max_pages=10`且单次响应上限300，
因此“六个月全量”不能仅靠当前测试命令可靠完成。需要先增加时间窗口或“翻页直到
发布日期早于截止日”的停止条件，再进行可恢复的分片采集。
