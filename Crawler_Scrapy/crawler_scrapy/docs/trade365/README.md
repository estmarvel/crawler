# 中招联合（山西）招标采购网爬取说明

## 1. 接入范围

目标入口：`http://shanxi.365trade.com.cn/zbgg/index.jhtml`

本 Spider 采集无需登录即可访问的三类公开栏目，并按工程、货物、服务继续细分：

| 源站目录 | 页面栏目 | 框架源类型 |
| --- | --- | --- |
| `/zbgg/` | 招标公告 | `tender` |
| `/bggg/` | 变更公告 | `change` |
| `/jggs/` | 结果公示 | `candidate`、`award` |

项目类型参数为：`engineering`（工程，`typeId=101`）、`goods`（货物，
`typeId=102`）、`service`（服务，`typeId=103`）。默认形成 4 个源类型 × 3 个项目类型，
共 12 个采集流。

公告列表、详情正文和正文内公开附件链接不需要登录。页面中的“我要参与”、招标文件获取、
投标和 CA 办理属于交易操作，本爬虫不登录、不提交报名，也不绕过 CA 或账户权限。

## 2. 爬取流程

该站使用服务端 HTML，无需调用隐藏 JSON 接口：

1. 根据栏目、项目类型和页码生成列表地址；第 1 页使用 `index.jhtml`，后续使用
   `index_2.jhtml` 等地址；
2. 从 `ul.searchList > li` 提取公告 ID、完整标题、发布日期、详情链接和页面项目类型；
3. 读取分页区中的总记录数和总页数，按日期范围、最大页数和每流最大记录数继续翻页；
4. 请求公开详情页，从 `.app h2` 读取标题、从页面元数据读取发布时间、从 `#content`
   保存正文 HTML 并清洗正文文本；
5. 根据详情标题纠正实际公告类型，构造统一字段，保存 JSON、HTML 快照、SHA256
   和 `_trace` 溯源包；
6. 公告阶段只登记正文里的真实公开文件链接，附件阶段再独立下载，避免大附件阻塞公告采集。

默认使用直连，并发 2，请求间隔 3～5 秒；每 400 个响应形成一个可恢复批次，批次间冷却
180～300 秒。出现 403、429 或访问校验时由统一直连保护中止当前批次，不通过提高并发强行重试。

## 3. 类型纠正和输出路由

源站栏目存在混栏：

- “变更公告”栏目同时包含控制价、延期、普通变更、终止/废标，以及二次招标公告；
- “结果公示”栏目同时包含中标候选人公示和中标结果公示。

因此最终类型不能直接照搬栏目。解析器根据标题纠正为：

- `tender`：招标公告；
- `correction`：变更、延期、控制价、澄清、答疑、补充、终止、废标、流标、撤销、
  暂停，以及候选人/结果更正，统一使用 `更正结果公示/CORRECTION` Schema；
- `candidate`：未发生更正的中标/成交候选人公示；
- `award`：中标/成交结果公示。

实际类型与工程/货物/服务组合后共有 12 个输出路由，例如
`中招联合山西_招标公告_工程.json`、`中招联合山西_更正结果公示_货物.json`。
源栏目保存在 payload 快照，源公告类型和最终 Schema 分别保存在
`_trace.fieldMeta.source_notice_type/schema_notice_type`。

## 4. 字段抽取

字段结构使用框架当前统一 Schema，不修改数据库。主要规则如下：

- 项目名称：以完整详情标题为主，删除公告类型和末尾标段说明；避免正文编辑器在括号内换行时
  把项目名截断；
- 项目编号：优先明确的“招标项目编号、采购项目编号、项目代码”，再使用独立“项目编号”；
- 招标编号：使用“招标编号、采购编号、代理编号”；少数模板同时存在“招标项目编号(I...)”
  和“项目编号(Q9...)”时分别保留两个源值，不丢失，也不把无标签编号盲目复制；
- 招标公告：抽取项目地点、规模、范围、资格条件、资金来源、工期/服务期/供货期、质量、
  文件获取时间、递交截止时间、开标时间/方式/地点、评标办法和保证金方式；
- 控制价公告：仅在正文明确披露单一总控制价时写入金额；多标段多个控制价保留在正文，
  不错误选取第一标段金额作为全项目金额；
- 更正结果公示：`公共类型`严格使用更正、变更、延期、终止、流标、废标、撤销等允许值，
  `公告内容`只保留实际变更事项并排除联系方式和签章页脚；
- 候选人公示：兼容含报价的 HTML 表格、无报价列表格，以及“第一中标候选人 + 投标报价”
  段落模板；表头中的元、万元、元/个、元/年等单位参与规范化，总金额换算为元，单价保留
  原精度和分母单位；没有披露报价时名称正常保存、报价保留空值；
- 结果公示：从表格或正文提取中标人、联合体、金额、工期和项目负责人；
- 联系方式：按招标人/采购人和代理机构分块抽取名称、地址、联系人和电话，并兼容
  “项目联系人、项目负责人、电话写联系人/联系电话写号码”等模板。

缺少明确来源的字段保持为空。完整正文和原始 HTML 始终保留，便于复核和后续规则升级。
源站日期范围出现结束日期早于开始日期时不擅自改写正文值，而是在
`_trace.fieldMeta.validation_warnings` 中记录 `SOURCE_DATE_RANGE_REVERSED`。

## 5. 快照、断点和附件

默认输出目录为 `output/trade365`：

- `json/`：按实际公告类型和项目类型拆分的 JSON；
- 正式运行不创建或更新 CSV；
- `snapshots/`：详情原始 HTML 快照；
- `attachments/`：第二阶段下载成功的公开附件；
- `state/notice_versions.json`：公告去重和内容版本状态；
- `state/jobs/`、`state/runner/`：Scrapy 与批次运行断点；
- `logs/`：批次实时日志。

每条 JSON 还包含详情地址、快照相对路径、快照 SHA256、内容指纹、解析版本和非空的字段缺失列表。
原始 HTML 只保存到快照文件，原始 payload 由 `_trace.payloadSnapshot` 引用。手动停止后再次使用相同范围运行，会利用 JOBDIR 和公告身份去重继续执行；
不会重新追加已经完成且正文未变化的公告。

附件只接受本站允许域名上的 HTTP/HTTPS 公开文件，且需要文件扩展名或明确下载路由。
普通网页链接不会被误判为附件。连接超时默认 30 秒、读取超时 900 秒、失败重试 4 次，
下载先写 `.part` 再原子改名。

## 6. 运行命令

在 `/home/intsig/Crawler_Scrapy` 执行：

```bash
# 最近 180 天：先爬公告和快照，再下载公开附件
./run_trade365.sh --phase all

# 全历史、全部栏目、工程/货物/服务
./run_trade365.sh --phase all --all

# 只爬公告，或只处理已有 JSON 中的附件
./run_trade365.sh --phase notices --all
./run_trade365.sh --phase attachments

# 每个源类型和项目类型取最近 5 条进行测试
./run_trade365.sh --phase notices --all --max-records 5 --max-pages 50

# 只爬招标公告的工程和服务类
./run_trade365.sh --phase notices --sections tender \
  --project-types engineering,service

# 指定日期范围
./run_trade365.sh --phase all --start-date 2026-01-01 --end-date 2026-08-06
```

`--phase all` 表示同一次运行中“公告完成后再下载附件”，并非无限循环。建议在 tmux 中运行：

```bash
tmux new -s trade365
cd /home/intsig/Crawler_Scrapy
./run_trade365.sh --phase all --all
# Ctrl-b，随后按 d，退出 tmux 但保持任务运行
tmux attach -t trade365
```

未改变公告 Schema 的解析规则升级，可以完全离线地用已保存的 HTML/payload 快照重算
JSON（不生成 CSV）：

```bash
python -m crawler_scrapy.sites.trade365.reparse_output --output-root new_output
```

该命令会先获得站点锁，再原子更新文件；不会请求网站，不写数据库。如果新版分类使公告
从招标/候选人变为更正结果公示，命令会拒绝在旧文件内原地改写，避免“文件名、顶层编码、
字段 Schema”不一致；这类记录应写入新的输出目录或使用专门的分类迁移。

## 7. 2026-08-06 实测结果

- 对 12 个源采集流分别请求最近 5 条，共导出 60 条详情；
- 72 个列表/详情请求全部为 HTTP 200，没有 403、429 或下载重试；
- 保存 60 份 HTML 快照，JSON 共 60 条；
- 历史输出曾包含招标公告 16 条、变更公告 9 条、终止公告 5 条、候选人公示 15 条、
  结果公示 15 条；v4 解析器重放时会将 14 条变更/终止及 1 条候选人更正统一纠正为
  `CORRECTION`，不会自动改写既有 JSON；
- 项目名称 60/60，招标人/采购人 60/60，代理机构 60/60；候选人名称 15/15，
  结果中标人 15/15；
- 项目编号 37/60、招标编号 53/60，未命中的记录正文没有对应明确标签，不进行猜测补齐；
- 样本正文没有真实公开文件附件；一条正文网页链接已验证不会再误识别为附件；
- 根据正文对比修复了括号换行导致项目名截断、双编号丢失、无报价候选人表、段落候选人、
  更正公告、单一控制价、网页误判附件、页脚签名误作项目经理、联合日期标签、联系人错位、
  联合体拆分、万元换算和单价精度等问题；当前解析版本为
  `trade365-v5-semantic-field-boundaries`。

AI 使用通用 C 方案：API/明确标签和规则证据充分的字段不调用模型；只有主要业务字段出现
“有标签未命中、HTML 残留、章节越界、名单与报价错位”等异常时，才把字段附近候选窗口
交给 GLM-5.2 复核，规则值和 AI 值均保留证据后再裁决。

本轮测试数据均位于 `new_output/trade365`，没有写入数据库。
