# SXJM 快照字段一致性审计与规则优化（2026-08-18）

## 1. 审计范围

本次只审计山西焦煤电子招采平台（SXJM），不访问源网站、不调用大模型、
不修改数据库，也不改写 `new_output/sxjm` 中的历史 JSON。

历史输出共 12 个 JSON 文件、26,595 条公告：

| 文件 | 条数 |
|---|---:|
| 依法项目_中标候选人公示 | 162 |
| 依法项目_招标计划 | 118 |
| 依法项目_招标（预审）公告 | 278 |
| 依法项目_终止公告 | 42 |
| 依法项目_结果公告 | 171 |
| 招标项目_中标候选人公示 | 2,015 |
| 招标项目_中标公告 | 2,188 |
| 招标项目_招标（预审）公告 | 2,983 |
| 招标项目_终止公告 | 90 |
| 简易采购限额以下_采购公告 | 7,094 |
| 非招项目_成交候选人公示 | 4,732 |
| 非招项目_采购（预审）公告 | 6,722 |

从每个文件固定随机抽取 25 条，共 300 条，使用 payload 中的详情 API 原值
和独立 HTML 快照重新运行最新版解析器，并将新结果与历史 JSON 对比。

## 2. 溯源完整性结论

- 抽样 300 条的 HTML 快照全部存在；
- 300 条快照的 SHA256 全部与 JSON 记录一致；
- HTML 快照字节与 payload 详情接口中的 `content` 全部一致；
- 因此当前主要问题是历史字段映射和解析边界，不是快照丢失或被改写；
- payload、HTML、详情 URL、公告 ID、内容指纹和解析版本能够形成完整溯源链。

附件元数据中的源文件 ID、文件名、URL、类型和下载状态仍独立保存。历史记录
中 `storage_path=null`、`parse_status=PENDING` 表示附件尚未实际下载或解析，不能
将“存在附件链接”误认为“附件文件已落盘”。本次没有重新下载附件，也没有审计
附件文件字节。

## 3. 发现的问题及优化

### 3.1 项目性质使用了源站频道名称

历史数据把“依法项目、招标项目、非招项目、简易采购限额以下”直接写入
`项目性质`，不符合最新版字段标准的枚举语义。

修改后：

- `依法项目` 映射为 `依法必须招标`；
- `非招项目`、`简易采购限额以下` 映射为 `非依法招标`；
- 普通 `招标项目` 频道没有充分证据时留空；
- 原频道继续保存在 `fieldMeta.channel`，不会丢失来源信息。

### 3.2 项目编号与招标编号混用

部分历史公告同时存在详情 API 的业务/招标编号和正文中的
`招标项目编号：D...`，历史结果把前者同时写入项目编号。

修改后：

- 项目编号只接受“招标项目编号、投资项目统一代码、项目代码、项目编号”；
- 招标编号只接受“招标编号、采购编号”，正文缺失时才回退 API
  `tender_number`；
- 支持“标签：编号”和“独立标签行 + 下一行编号”两种正文模板；
- `项目编号/招标编号` 由两个标准字段去重派生，不单独猜测；
- 编号必须含数字并保持括号配对，只有机构前缀的值不作为公告级编号。

抽样中有 59 条项目编号会由旧业务编号修正为正文明确的项目编号，40 条组合
编号相应得到补全。公告 26194 的正文明确写的是
`采购编号：fxkyzxfw202502102`，因此新版保留正文原值，不猜测添加历史结果中的
`ZC` 前缀。

### 3.3 项目名称夹带公告类型和轮次

历史结果存在“招标计划变更公告、资格预审公告、招标暂停公告、【二次】、
(第2次招标)、招标三次延期公告”等后缀或阶段标记。

修改后只删除公告类型和有明确边界的轮次标记，同时保留项目名本身合法的
`（002标段）`、`（第一批）` 等内容，也不会误删“二次供水工程”中的“二次”。

### 3.4 资格预审公告误用招标公告字段

源站把招标和资格预审放在同一栏目。历史输出统一按招标公告 Schema 保存，
空“采购范围”标题还会越界吞入整段资格要求。

修改后根据标题中的“资格预审/资审公告”切换到 `资格预审公告` Schema，使用
`项目概况与招标范围`，资格要求与预审文件获取信息保持独立，并输出到单独的
资格预审 JSON/CSV 文件。

### 3.5 终止、变更、延期等误用招标公告字段

历史终止公告套用 `招标公告` Schema，导致大量无意义空字段；依法项目聚合栏目
中的变更、延期、更正、澄清、撤销、流标和废标公告也存在同样问题。抽样中有
64 条历史记录不具备最新版更正类 Schema 的字段。

修改后这些公告统一使用最新版 `更正结果公示` Schema：

- `公共类型` 保存更正、变更、澄清、延期、终止、流标、废标、撤销或其他；
- `公告内容` 保存“一、内容”或明确原因章节中的实际变化内容；
- 保留“原信息内容/现变更为”的对应关系；
- 更正公告有多个开标时间时取最后一个明确值作为最终有效时间；
- 顶层监督部门和联系方式不会混入公告内容；
- 源站栏目和原始公告性质继续保存在 fieldMeta 中。

### 3.6 代理机构被人员名或内部账号污染

详情 API 的 `tendering_agency` 偶尔返回 `王国玺(FX)`、`郭亚雄(SM)` 一类
经办人/内部账号。抽样中发现 24 条此类历史值。

修改后正文明确标注的代理机构名称优先；API 回退值必须具有公司、集团、中心、
事务所、研究院、招标代理、工程咨询或项目管理等组织特征，否则留空。

### 3.7 质量要求和行业占位值

- 旧规则把“其他要求”当作质量要求，可能把运输、付款等条款错误写入质量字段；
- `无、暂无、/、-` 等占位值曾被保存为所属行业或质量要求。

修改后质量要求只接受质量、验收、技术或服务标准的明确标签，占位值统一为空。

### 3.8 获取、递交和章节边界

- 空章节遇到下一章节时立即停止，不再吞并资格条件；
- 资格预审文件、招标文件、采购文件分别支持对应标题；
- “递交地址：”为空标签时可读取紧邻下一行的上传/现场递交操作；
- 递交截止时间优先使用正文明确值，不再无条件复制开标时间。

### 3.9 候选人/中标人与报价对应

候选人名称、候选人报价、中标人名称和中标价按原表格顺序保存。某一主体未公布
报价时，对应位置使用 `null`，不再把整个价格数组变成空数组，避免列表错位。

## 4. 与最新版预设字段的对应关系

当前 SXJM 实际覆盖以下 6 种最新版公共 Schema：

| 源站公告 | 公共 Schema | 数据库类型编码 |
|---|---|---|
| 招标计划 | 招标计划 | PLAN |
| 资格预审/资审公告 | 资格预审公告 | PREQUALIFICATION |
| 招标公告、采购公告 | 招标公告 | TENDER |
| 中标/成交候选人公示 | 中标候选人公示 | CANDIDATE |
| 中标结果、成交公告 | 中标结果公示 | AWARD |
| 变更、更正、澄清、延期、终止、撤销、流标、废标 | 更正结果公示 | CORRECTION |

解析器已增加自动化断言：每一种上述公告的业务字段集合必须与
`ANNOUNCEMENT_SCHEMAS` 完全相同，既不能缺少预设字段，也不能增加数据库契约
之外的业务字段。源站特有信息只进入顶层元数据、fieldMeta 或独立溯源文件。

SXJM 当前没有定标候选人和合同履约栏目，因此不会为了“凑齐八类”生成空的
`定标候选人公示` 或 `合同与履约` 数据。

## 5. 不属于提取错误的差异

离线重放中以下差异是历史导出规范化造成的表示差异，不是正文提取错误：

- 历史 datetime 的 `.000` 与解析器原值精确到秒；
- 历史金额已转换为元和浮点/Decimal，新解析器原始阶段仍可能是带单位字符串；
- 历史空 Decimal 为 `null`，原始解析阶段为空字符串；
- 历史价格为数值，新解析阶段保留数字字符串，后续 Schema 管线统一转换。

最终 JSON/数据库写入前仍由公共 Schema 管线执行日期时间、金额、列表和空值的
标准化。

## 6. 当前限制与后续处理

1. 本次只修改未来解析和导出的代码，没有改写 parser v12 生成的历史 JSON；
2. 历史终止/更正类记录若要使用新 Schema，需要另行执行离线重解析或重新采集；
3. 未在 API/正文中明确出现的字段继续留空，不允许规则或 AI 猜测；
4. 仅存在于 PDF/附件中的业务字段，需要附件下载并完成文本提取后才能补充；
5. 本次未进行真实网站请求、AI 调用和数据库导入验证。

下一站审计应继续使用相同顺序：历史 JSON 全量计数 → 分类型快照抽样 → 字段
证据对比 → 最新 Schema 集合检查 → 规则修复 → 定向与全量回归。
