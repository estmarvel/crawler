# 山西焦煤字段来源与提取规则

本文件中的“目标字段”沿用项目公共 Schema（即 SJQ 使用的字段集合），但所有来源和解析规则均针对山西焦煤电子招采平台重新建立。

## 页面与接口结构

- 首页 `/home/homePage` 是 Umi 单页应用，HTML 只提供 `root-master` 容器，实际频道与公告由前端脚本加载。
- 列表接口 `/api/portal/v1/announcement/index` 提供公告 ID、标题、公告类型、频道分类和发布时间，用于分页与详情链接构造。
- 详情页 `/home/detail?id={id}` 使用详情接口 `/api/portal/v1/announcement/details/{id}`；接口响应为 AES-128-CBC 加密 JSON。
- 详情 JSON 的独立字段优先用于稳定元数据；`content` HTML 用于正文段落、联系方式和结果表格；`document` 用于附件。
- `_trace.payload.list/detail` 保存解密后的原始列表和详情对象；`transport` 保存列表请求参数、分页、列表/详情响应元数据和接口业务状态。加密密文本身不重复保存。

## 四个频道与公告类型

- 依法项目：招标计划 19、招标（预审）及其他公告 8、候选人 2、结果 10、终止 4。2026-08-04 实际接口验证 `category=1&type=1` 的 `total=0`，普通招标公告同样由 type 8 返回，因此不再发送空 type 1 请求。
- 招标项目：招标公告 1、候选人 2、中标结果 3、终止 4。
- 非招项目：采购公告 5、成交候选人 6、成交结果 7、终止 4。
- 简易采购限额以下：采购公告 5、成交结果 7、终止 4。

## 公共字段

- 项目性质：由列表请求的 `category` 所属频道确定，不从标题猜测。
- 源站公告性质：默认由频道栏目和 `announcement_type` 确定；对被源站放在“其他/采购”栏目中的延期、变更、更正、撤销和终止公告，再以完整标题纠正实际性质。
- 项目名称：优先正文“项目名称/采购项目名称”，其次详情 `project_name`，最后清理详情 `title` 的公告类型后缀。
- 所属行业：详情 `industry_category`。
- 组织形式：正文“组织形式”优先；详情 `tendering_method` 为自行时输出自行招标；存在正式代理机构时判定委托招标。
- 发布日期：详情 `publish_time_format`；若网站返回 1970 时间则回退 `created_at_format`。
- 发布网站：固定为山西焦煤电子招采平台。
- 公告正文：详情 `content` 按 DOM 原始顺序清洗，段落和表格单元格均保留，避免把所有结果表移动到正文开头。
- 详情页链接：列表公告 ID 构造 `/home/detail?id={id}`。
- 附件：详情 `document` 中的 ID、原文件名、MIME 类型和 `path`。

## 招标计划字段

- 招标方式、项目名称、项目类型、项目总投资、招标内容、招标人名称、行政监督部门、建设地点、建设内容及规模、预计发布时间：优先使用详情接口对应的 `tender_mode`、`project_name`、`type_project`、`contribution_scale`、`tender_content`、`legal_person`、`supervise_dept_name`、`project_address`、`project_scale`、`notice_plan_send_time`，缺失时再识别正文同名标签。

## 招标公告与采购公告字段

- 开标时间、文件获取时间：分别取详情 `bid_opening_date_format` 和 `sale_begin_time_format` 至 `sale_end_time_format`。
- 项目编号/招标编号：优先正文展示的“项目编号/招标项目编号/招标编号/采购编号”，其次 `tender_number`，最后才使用内部 `code`。
- 项目类型/行业分类：详情 `project_type` 映射为货物、工程、服务；缺失时回退 `industry_category`。
- 项目总投资/估算金额、招标金额：识别正文同名标签及“最高限价、采购预算”。
- 资金来源：识别正文“资金来源/项目资金来源”及“项目资金来源为……”句式。
- 项目地点：优先正文“项目地点、建设地点、服务地点、交货地点、实施地点”，缺失时回退详情 `region`。
- 招标人/采购人名称：取正文正式联系方式区或正文“招标人/采购人”，不能使用详情中的项目经理账号；简易采购正文缺失时才使用详情 `tenderer`。
- 项目规模：识别“项目规模、建设规模、采购项目概况、项目概况”。
- 工期/服务期/供货日期：识别“合同履行期限、履约期限、工期、计划工期、服务期限、服务周期、服务期、供货期限、供货期、交货期限、交货期”。
- 质量要求：识别“质量要求或服务标准、质量要求、质量标准、服务标准、其他要求”。
- 招标内容与范围：截取本站“项目概况和招标范围/采购范围及相关要求/采购范围/招标范围”章节，保留标题同行内容，截止到资格要求章节。
- 申请人/投标人资格要求：截取“供应商资格要求、供应商资质要求、投标人资格要求、申请人资格要求”章节，截止到文件获取或递交章节。
- 获取方式：优先截取“采购文件的获取/招标文件的获取”章节；没有章节标题的非招模板直接取“获取方式/获取方法”。
- 递交截止时间、开启时间：详情开标时间优先，正文标签作为补充。
- 递交方法、开启方式、开启地点、评审办法、投标保证金方式：分别识别详情正文对应标签。
- 招标人和代理机构地址、联系人、电话：按正文最后的“联系方式”区建立招标人/采购人和代理机构状态，后出现的正式联系方式覆盖前面的异议/监督信息。

## 候选人公示字段

- 公示时间：详情 `sale_begin_time_format` 至 `sale_end_time_format`，缺失时识别正文“公示开始/结束时间、公示期”。
- 招标编号/项目编号：按正文、`tender_number`、`code` 的优先级提取。
- 中标/成交/入围候选供应商名称和报价：直接解析 `content` 原始 HTML 表格，兼容“候选人名称、候选供应商名称、入围候选供应商名称”等表头，按表头定位名称列和报价列，不依赖固定列号。
- 中标候选人明细：将正文依次出现的“标段名称”与各结果表格按顺序绑定，保存标段、候选人名称、候选人报价。
- 表格没有报价列时，明细中的报价为 `null`，顶层报价数组保持空并进入“缺失字段”，不再把一组空值误判为有效报价。
- 联系方式：使用本站正文联系方式状态解析，不使用 SJQ 页面选择器。

## 中标与成交结果字段

- 招标方式：正文“招标方式/采购方式/采购方法”优先，缺失时使用详情 `tendering_method`。
- 中标/成交人名称和金额：解析原始 HTML 表格，通过“中标人名称、成交人名称、供应商名称”和“报价、中标价、成交价、中标金额、成交金额”等表头定位。
- 中标结果明细：按正文“标段名称”顺序绑定每张结果表格。
- 联合体成员、工期、项目经理、项目经理证书名称及编号、依据文件及文号：仅在正文出现相应标签时提取；源公告未提供则保持空值。
- 联系方式：取正文正式联系方式区；详情 `tendering_agency` 只作为正文缺失时的代理机构回退值。

## 空值原则

- 字段在本站接口、正文和表格中均不存在时保留空值，不用其他字段臆测填充。
- 终止公告通常只提供项目编号、终止原因和联系方式，因此招标范围、资格条件、评审办法等为空属于源公告真实缺失。
- 表格没有报价列时，中标价/候选人报价保持空值，不能把排序数字误当金额。
- 未填写的官方空模板及“（项目名称）成交结果公告”等占位符不作为成交人；完整原文和附件仍保留，供后续人工或附件解析追溯。
- 超长中文附件名只在本地对象路径中按 UTF-8 字节安全截断并追加原名哈希，JSON 中的原始文件名不变。
