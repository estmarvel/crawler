> 版本：2026-08-14-v1  
> 适用范围：`Crawler_Scrapy` 中已接入统一公告 Schema 的站点

> 实现状态：已在千极链混合 AI 链路实施 C2 方案。通用字段契约和
> 候选窗口位于 `crawler_scrapy/ai/field_contracts.py`，站点裁决链路位于

## 1. 目的与边界

本文档只定义需要准确提取并进入数据库或
`project_notice.structured_data` 的公告业务字段。

下列内容不属于 AI 业务字段提取范围：

- 公告正文和原始 API payload；
- HTML/PDF/附件快照、存储路径和 SHA256；
- 详情页链接、源站公告 ID、爬虫时间和内容指纹；
- 解析状态、抽取方式、`crawlerVersion`、`extractionVersion`
  和核验状态；
- 附件的文件名、URL、存储对象、大小、哈希和解析状态。

这些信息仍必须保存以满足溯源和附件入库要求，但不由 AI
提取，也不参与业务字段缺失率计算。

## 2. 复核后的关键决定

### 2.1 项目性质不可简单二选一

初稿将项目性质限制为“依法必须招标/非依法招标”，会导致
源站明确存在的“其他必须招标”被错误归类。最终标准值为：

1. `依法必须招标`；
2. `非依法招标`；
3. `其他必须招标`；
4. 空值：源站和正文都无法确定。

站点别名只能通过已验证的固定映射转换。例如，“依法项目”可
映射为“依法必须招标”；“招标信息”不是项目性质，应输出空值。
“自主发布”、“企业采购”、“简易采购限额以下”只有在站点规则
已确认其法律性质时才能映射，禁止 AI 自行判断。

### 2.2 区分项目类型、行业和招标方式

- `项目类型`：招标计划中可保留“房屋市政、交通、农业、能源”等
  源站明确分类，不强制压缩为工程/货物/服务。
- `项目类型/行业分类`：资格预审和招标公告优先保留源站的
  标准类别；源站只给出“工程/货物/服务”时保留该值。
- `所属行业`：必须来自源站分类或正文明确标签，不根据
  项目名称、企业名称或 AI 常识推测。
- `招标方式`：可保留源站明确的公开招标、邀请招标、询比、
  询价、竞争性磋商、竞争性谈判、单一来源和框架协议等明确值。
- `组织形式`：只保存“委托招标、自行招标”等组织关系，
  不得与招标方式混用。

### 2.3 地点粒度与数据库映射

`Project` 使用 `province`、`city` 和 `location_text` 保存项目地点。
结构化字段 `项目地点`、`建设地点` 必须保留源文明确给出的完整履约地点：

例如：

| 正文或候选值 | 结构化结果 |
|---|---|
| `山西省晋城市陵川县平城镇` | `山西省晋城市陵川县平城镇` |
| `沁水县郑村镇肖庄村` | `沁水县郑村镇肖庄村` |
| `供货地点：山西省文水中学校` | `山西省文水中学校` |
| `太原市小店区` | `太原市小店区`；不得用模型补写正文没有的省份 |

镇、乡、村、道路、门牌、矿区和厂区等详细信息继续存在公告正文
和快照中，不进入该结构化字段。招标人和代理机构地址不受此限制，
应保留源文完整地址。

### 2.4 候选人、中标人与报价必须成对

候选人/定标候选人/中标人名称与其报价必须保持原始顺序和
相同索引。名称存在而价格未公布时，报价列表对应位置使用
`null`，不得删除占位导致错配。

### 2.5 长文本字段不得由 AI 摘要

招标范围、资格要求、建设规模、更正内容和合同主要内容等字段
可以由 AI 辅助确定起止边界、清除 HTML 和排除串入段落，但不允许
改写、归纳或缩写法律要求。

## 3. 全局抽取规则

### 3.1 证据优先级

1. 已验证语义的源站 API 字段；
2. HTML/PDF 中明确的标签-值、表格行或完整章节；
3. 公告标题，仅用于项目名称和公告子类型等少数字段；
4. AI 对上述证据的边界识别和冲突复核。

AI 不是独立事实来源。每个 AI 候选值都必须附带原文证据、
原文偏移和候选窗口 ID；无证据时必须输出空值。

### 3.2 空值

| 字段类型 | 无证据时的标准值 |
|---|---|
| 普通字符串 | `""` |
| 日期、时间、十进制金额 | `null` |
| 名称、企业、报价列表 | `[]` |
| 对象列表 | `[]` |

禁止用模型生成的“未提及、未知、暂无、不详”填补空值。
源公告明确写明“无”或“不接受联合体”时，可保留该明确语义。

### 3.3 时间

- 有秒：`YYYY-MM-DD HH:mm:ss`；
- 只到分：秒补 `00`；
- 只有日期：`YYYY-MM-DD`；
- 时间范围：`开始时间 — 结束时间`；
- 只公布月份或季度：保留原始精度，不虚构日期。

`开标时间`、`递交截止时间`、`开启时间`只能根据各自明确标签
提取，不因为它们数值相同就相互复制。更正公告中只保存更正后
最终有效值，原值保留在公告正文中。

### 3.4 金额

`项目总投资`、`项目总投资/估算金额`、`招标金额`、`合同金额`
映射到数据库时统一换算为人民币元，保留两位小数：

```text
26834.47万元 -> 268344700.00
1.25亿元     -> 125000000.00
```

下列内容不得写入数据库总金额列：

- 百分比、费率、折扣；
- 元/吨、元/年等单价；
- 不超过审定金额的 95% 等相对报价；
- 同一候选段中有多个金额且无法判定总额。

这类值可在 `structured_data` 中保留规范化的原始字符串，
关系表的 `bid_amount` 等 Decimal 列应为空。

### 3.5 项目编号与招标编号

#### 项目编号

仅接受：

- 站点映射已确认为项目编号的 API `projectCode` 或等价字段；
- 正文明确标注“项目编号、项目代码、项目编码”的值。

禁止把招标编号、采购编号、标段编号、包号、公告 ID、交易 ID、
审批文号或 URL 中的普通记录 ID 当作项目编号。

#### 招标编号

仅接受：

- 站点映射已确认为招标/采购编号的 API 字段；
- 正文明确标注“招标编号、采购编号、采购项目编号”的值。

标段编号只有在源站明确定义其等同于招标编号时才能使用。

#### 兼容组合字段

`项目编号/招标编号`和`招标编号/项目编号`只作为旧数据和
Excel 字段的兼容输出：

1. 先分别提取标准的`项目编号`和`招标编号`；
2. 由程序生成组合字段；
3. 组合字段不再独立调用 AI；
4. 只有招标编号时，项目编号必须为空，禁止相互复制。

### 3.6 企业、联系人与联系方式

- 企业名称保存源文完整法定名称，不附加地址、人名和电话；
- 联系人只保存人名，不保存职务标签和电话；
- 联系方式只保存电话、手机、邮箱等值，保留源站脱敏符号；
- 多个值按原文顺序使用中文分号分隔；
- 招标人、代理机构和监督部门的名称、地址、联系人和电话
  必须在同一角色区块中取值，禁止跨块串联；
- 企业简称不得由 AI 扩写为未经证实的全称。

下列 Excel/Schema 字段共用该规则，但必须分别输出，不能合并为
一个“联系信息”字段：

| 角色 | 名称字段 | 地址字段 | 联系人字段 | 联系方式字段 |
|---|---|---|---|---|
| 招标人/采购人 | `招标人名称`、`招标人/采购人名称`、`招标人/采购人` | `招标人地址` | `招标人联系人` | `招标人联系方式` |
| 招标代理机构 | `招标代理机构` | `招标代理机构地址` | `招标代理机构联系人` | `招标代理机构联系方式` |
| 监督部门 | 当前更正 Schema 无独立名称字段 | `监督部门地址` | `监督部门联系人` | `监督部门联系方式` |

注意：资格预审和招标公告的 Excel 中 `招标代理机构` 重复出现，
当前 Schema 只保留一个标准字段，不重复输出。

### 3.7 发布信息

`发布日期`优先使用 API 或详情页元数据，`发布网站`使用站点
配置中的固定官方名称。二者不调用 AI，也不从页脚、转载声明
或正文签章中推测。

## 4. 招标计划

| 字段 | 格式/类型 | 严格定义与排除项 |

| 项目性质 | 枚举字符串 | 使用 2.1 规则；无确定证据时为空 |
| 招标方式 | 字符串 | 只保留源站/API/正文明确的招采方式 |

| 项目编号 | 字符串 | 执行 3.5 编号规则 |
| 招标编号 | 字符串 | 额外的公告关联字段；无证据时为空 |
| 项目类型 | 字符串 | 优先源站标准分类，如房屋市政、交通、农业、能源 |
| 项目总投资 | Decimal/元 | 项目整体投资；不得使用单个标段金额或年度预算代替 |
| 招标内容 | 纯文本 | 计划招标的工程、货物或服务内容；排除联系信息和发布时间 |
| 招标人名称 | 字符串 | 完整法定名称 |
| 行政监督部门 | 字符串 | 只保存部门名称，不混入地址和电话 |

| 招标公告（资格预审公告）预计发布时间 | 日期/范围文本 | 保留源文精度，可为具体日期、月份或季度 |
| 发布日期 | 日期时间 | 源站直取，不调用 AI |
| 发布网站 | 字符串 | 站点配置固定值，不调用 AI |

|---|---|---|
| 项目性质、项目名称、项目编号、招标编号 | 标量字符串 | 执行全局性质、名称和编号规则 |
| 所属行业 | 字符串 | 仅取源站分类或正文明确标签，不推测 |
| 组织形式 | 枚举字符串 | 例如委托招标、自行招标；不得填公开招标 |
| 开标时间 | 日期时间 | 只取明确的开标时间，不使用公示或截止时间替代 |
| 项目编号/招标编号 | 兼容字符串 | 由两个标准编号派生，不单独调用 AI |
| 项目类型/行业分类 | 字符串 | 保留源站标准分类；不把项目名称当成分类 |
| 项目总投资/估算金额 | Decimal/元 | 项目整体投资或明确估算金额 |

| 资金来源 | 字符串 | 只保存企业自筹、财政资金、银行贷款等来源；排除招标人信息 |
| 项目地点 | 地点原文 | 保留学校、厂区、矿区、园区、道路等具体地点；不得误取招标人/代理地址或文件递交地址 |
| 招标人/采购人名称 | 字符串 | 完整法定名称 |
| 项目概况与招标范围 | 纯文本 | 保存概况和本次预审范围；不混入资格要求 |
| 申请人资格要求/投标人资格要求 | 纯文本 | 完整保留资质、业绩、人员、财务、信誉和联合体条件，不摘要 |
| 预审文件获取时间 | 时间范围 | 开始与截止时间；原文只有一端时不补另一端 |
| 获取方式 | 纯文本 | 只保存登录、下载、领取等实际操作；排除售价、时间和逾期提示 |
| 递交截止时间 | 日期时间 | 资格预审申请文件的最终截止时刻 |
| 递交方法 | 纯文本 | 仅保存上传、现场递交、邮寄等操作；排除拒收和逾期条款 |
| 开启时间 | 日期时间 | 只取明确的预审文件开启时间 |
| 开启方式 | 字符串 | 线上、不见面、现场等明确方式 |
| 开启地点 | 字符串 | 保留完整场所或平台名称，不执行区/县截断 |
| 评审办法 | 字符串/纯文本 | 明确办法名称或完整评审说明，不自行归类 |
| 投标保证金方式 | 字符串 | 只保留现金、保函、保证保险等方式，不混入保证金金额 |
| 招标人和代理机构名称/地址/联系人/联系方式 | 字符串 | 按角色块分离；不得串行或跨角色填充 |
| 发布日期、发布网站 | 源站字段 | 直接取源站，不调用 AI |

## 6. 招标公告

资格预审公告的共同字段执行第 5 节相同标准。招标公告额外或
有不同语义的字段如下：

| 字段 | 格式/类型 | 严格定义与排除项 |
|---|---|---|
| 项目规模 | 纯文本 | 项目数量、面积、容量、里程、等级等客观规模；不复制整个招标范围 |
| 工期/服务期/供货日期 | 字符串 | 保留完整原文，如“180日历天”、“合同签订后30日内”，不强制换算 |
| 质量要求 | 纯文本 | 只保存质量、验收或技术标准；不混入投标人资格条件 |
| 招标内容与范围 | 纯文本 | 本次招标包含的工作、货物、服务、标段和工作边界；不保存项目背景 |
| 申请人资格要求/投标人资格要求 | 纯文本 | 完整保留资质、人员、业绩、财务、信誉和联合体条件 |
| 预审文件获取时间 | 时间范围 | 字段名按 Excel 和当前 Schema 保留；在普通招标公告中实际语义为“招标文件获取时间” |
| 获取方式 | 纯文本 | 仅获取操作，不带时间、售价和逾期提示 |
| 递交截止时间 | 日期时间 | 投标文件的最终截止时刻，不从开标时间复制 |
| 递交方法 | 纯文本 | 仅上传、现场递交等操作，排除拒收条款 |
| 开启时间/方式/地点 | 时间和字符串 | 只在正文有各自明确标签时填充，不与开标字段自动复制 |
| 评审办法 | 字符串/纯文本 | 明确办法名称或完整说明，不由 AI 判断法定分类 |
| 投标保证金方式 | 字符串 | 只保存担保方式，不混入金额和缴纳截止时间 |

必须保持以下语义分离：

- `项目规模`：项目有多大；
- `招标内容与范围`：本次招什么；
- `工期/服务期/供货日期`：何时或多久完成；
- `质量要求`：应达到什么标准。

## 7. 中标候选人公示

| 字段 | 格式/类型 | 严格定义与排除项 |
|---|---|---|
| 项目性质、项目名称、所属行业、组织形式 | 标量字符串 | 执行全局定义，不根据候选人业务范围反推行业 |
| 开标时间 | 日期时间 | 实际开标时间，不是公示开始时间 |
| 公示时间 | 时间范围 | 保存公示开始和结束时间；只有一端时不虚构另一端 |
| 项目编号、招标编号、招标编号/项目编号 | 字符串 | 两个标准编号分别提取，组合字段程序派生 |
| 中标候选人名称 | 字符串列表 | 按第一、第二、第三候选人原始顺序；保存完整法定名称 |
| 中标候选人报价 | 金额/原始报价列表 | 与候选人名称等长并按索引对应；缺价位置使用 `null` |
| 招标人/采购人和代理机构信息 | 字符串 | 名称、地址、联系人、联系方式在对应角色块中取值 |
| 发布日期、发布网站 | 源站字段 | 直取，不调用 AI |

示例：

```json
{
  "中标候选人名称": ["甲公司", "乙公司", "丙公司"],
  "中标候选人报价": [1000000.00, 1050000.00, null]
}
```

费率、折扣、单价等非总额可保留原始字符串，例如 `"95%"`。

## 8. 定标候选人公示

公示时间、候选人名称和报价按第 7 节的同等规则处理。

| 字段 | 格式/类型 | 严格定义与排除项 |
|---|---|---|
| 定标候选人名称 | 字符串列表 | 按源文顺序保存，不由 AI 重排 |
| 定标候选人报价 | 报价列表 | 与候选人名称等长、同索引 |
| 定标候选人项目经理 | 字符串 | 必须与对应候选人处于同一表格行或内容块 |
| 定标候选人项目经理相关证书及编号 | 字符串 | 保留证书名称和编号，不混入身份证号和其他人员编号 |
| 定标候选人项目副经理 | 字符串 | 只在公告明确公布时提取 |
| 定标候选人项目副经理相关证书及编号 | 字符串 | 必须与项目副经理一一对应 |
| 定标候选人资信情况 | 纯文本 | 保存公告明确列出的资信，不由 AI 评价或排名 |
| 定标候选人业绩情况（名称、日期、金额） | 纯文本 | 保存项目名称、日期、金额的原始对应；当前投标报价不是业绩金额 |
| 依据文件 | 字符串 | 法律、法规、招标文件、评标报告等明确文件名称 |
| 依据文号 | 字符串 | 只保存明确文号，不提取章节号、网页编号或公告 ID |
| 招标人/采购人、代理机构、发布信息 | 字符串/时间 | 执行全局角色分离和源站直取规则 |

多候选人时，人员、资信和业绩字段必须保留归属。在现有字符串
字段中建议使用：

```text
甲公司：项目经理张三，证书……；乙公司：项目经理李四，证书……
```

## 9. 中标结果公示

| 字段 | 格式/类型 | 严格定义与排除项 |
|---|---|---|
| 项目性质、项目名称、项目编号、招标编号 | 标量字符串 | 执行全局标准；项目编号和招标编号不混用 |
| 所属行业、组织形式、招标方式 | 字符串 | 只保存源站或公告明确值，三者语义独立 |
| 中标人名称 | 字符串列表 | 按标段或源文顺序保存完整法定名称 |
| 联合体成员 | 字符串列表 | 仅公告明确存在时提取；已明确的牵头人不重复放入成员列表 |
| 中标价 | 金额/原始报价列表 | 与中标人名称等长、同索引；费率和折扣保留原始字符串 |
| 工期 | 字符串 | 保存中标结果确定的最终工期，不用招标公告计划工期覆盖 |
| 项目经理 | 字符串 | 必须与对应中标人处于同一表格行或内容块 |
| 项目经理证书名称 | 字符串 | 必须与项目经理对应，只保存证书名称 |
| 项目经理证书编号 | 字符串 | 必须与项目经理对应；不得误取公司信用代码 |
| 招标人/采购人、代理机构 | 角色字段 | 名称、地址、联系人和联系方式分角色提取 |
| 依据文件、依据文号 | 字符串 | 仅在公告明确列出时提取 |
| 发布日期、发布网站 | 源站字段 | 直取，不调用 AI |

多标段时，中标人和中标价必须保持原始顺序。无法证明对应关系时，
宁可将价格设为 `null`，不允许 AI 自行配对。

## 10. 更正结果公示

当前 Schema 按 Excel 保留了字段名 `公共类型`。该名称可能是
“公告类型”的历史命名，为了不改变当前输出和导入契约，暂不重命名，
但其业务语义固定为“更正类公告的子类型”。

`公共类型` 允许值：

- `更正公告`；
- `变更公告`；
- `澄清公告`；
- `延期公告`；
- `终止公告`；
- `流标公告`；
- `废标公告`；
- `撤销公告`；
- `重新招标公告`；
- `其他`。

| 字段 | 格式/类型 | 严格定义与排除项 |
|---|---|---|
| 公共类型 | 枚举字符串 | 优先源站分类，其次根据标题明确关键词映射；不由 AI 推测业务原因 |
| 项目名称 | 字符串 | 指向原项目；删除更正、延期、终止等公告类型后缀 |
| 项目编号、招标编号 | 字符串 | 执行编号严格证据规则 |
| 所属行业、组织形式 | 字符串 | 只保存明确源值，不根据原项目推测 |
| 开标时间 | 日期时间 | 只保存更正后最终有效的开标时间 |
| 标书发售时间 | 时间范围 | 只保存更正后最终有效的发售/获取时间范围 |
| 公告内容 | 纯文本 | 保存实际变更事项、变更前后值、终止/废标原因；不复制完整网页模板 |
| 招标人、代理机构、监督部门地址/联系人/联系方式 | 角色字段 | 必须在各自角色块内提取，不跨块串联 |
| 依据文件、依据文号 | 字符串 | 文件名称与文号分开；章节号、公告 ID 不属于依据文号 |
| 发布日期、发布网站 | 源站字段 | 当前更正公告自身的发布信息，不是原公告发布时间 |

更正公告必须在同一候选窗口或完整变更章节中同时保留“原内容”和
“变更后内容”，避免将原值写成最终值。

## 12. AI 使用分级（为后续 C 方案提供输入）

### 12.1 不调用 AI 的字段

- 发布日期、发布网站；
- 站点配置能直接确定的项目性质和公告类型；
- 已验证 API 中的项目编号、招标编号、行业和类型；
- 附件和溯源元数据；
- 表格结构完整且可以稳定对齐的候选人/中标人、排名和报价。

### 12.2 默认规则提取，冲突时才调用 AI

- 项目名称；
- 项目编号和招标编号的 HTML 标签值；
- 时间和金额；
- 企业名称、联系人和联系方式；
- HTML 结构损坏后的候选人-报价对应关系；
- 更正前后时间、金额的最终有效值判定。

### 12.3 适合候选窗口 AI 的字段

- 资金来源；
- 项目规模和建设内容及规模；
- 项目概况与招标范围；
- 招标内容与范围；
- 申请人/投标人资格要求；
- 质量要求；
- 获取方式和递交方法；
- 投标保证金方式；
- 更正公告的实际变更内容；
- 合同主要内容。

AI 的主要任务是判断字段边界、排除串入内容和选择有效版本，
而不是重新创作字段内容。

## 13. 入库对应性

上述标准不需要改变数据库结构：

- 项目名称、性质、行业、类型、招标方式、组织形式、地点、
  金额、资金来源、开标时间、工期和质量要求可对应 `Project`；
- 公告标题、正文、公告类型、发布信息和完整业务字段对应
  `ProjectNotice` 及 `structured_data`；
- 候选人、中标人、联合体、排名、金额和项目经理对应
  `ProjectCompanyRelation`、`ProjectConsortiumMember` 和
  `ProjectCompanyPerson`；
- 资格要求等长文本可对应 `ProjectRequirement`；
- 合同名称、双方、金额、日期和主要内容对应 `Contract`；
- 原始附件和公告附件分别对应 `RawNoticeAttachment` 和
  `ProjectNoticeAttachment`；
- AI 抽取模型、版本、置信度和验证状态对应 `NoticeExtraction`。

## 14. C2 方案的验收条件

实施“候选窗口和原文行号 -> AI 边界/值提取 -> 本地原文切片与验证 -> 冲突时扩大章节”后，
至少需满足：

1. 所有 AI 采纳值均有原文证据和偏移；
2. 项目地点保留源文精度，可到学校、厂区、矿区、园区或道路，但不得混入招标人/代理地址和文件递交地址；
3. 项目编号和招标编号不相互复制；
4. 候选人/中标人与报价数组等长、同索引；
5. 长文本不含 HTML、不串入下一章节、不被 AI 摘要；
6. 时间和金额不丢单位、不虚构精度；
7. 更正公告的结构化值使用更正后最终值；
8. AI 超时或输出不合法时不影响公告、快照和附件保存；
9. AI 无法证实的候选值不覆盖可验证的 API 或规则值；
10. 重复运行不重复生成公告、附件或数据库记录。
11. 长文本最终值必须由程序按原文行范围切片，模型不得摘要或重写；
12. 非空规则值只有在首轮和扩展阶段 AI 结果一致且本地验证通过时才允许覆盖；
13. 八类公告全部预设字段必须具有明确类型、定义、候选标签和必要排除项。
