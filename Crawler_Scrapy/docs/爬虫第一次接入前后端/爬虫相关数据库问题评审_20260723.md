# 爬虫核心表数据库结构问题评审

> 文档用途：数据库结构专项评审，可直接复制到飞书文档  
> 评审日期：2026-07-23  
> 评审范围：`data_source`、`crawl_task`、`raw_notice`、`notice_extraction`、`project`、`project_notice`、`project_requirement`  
> 说明：本文只讨论表结构、字段职责、表间关系、重复字段和约束，不讨论数据导入和业务数据现状

---

## 一、总体结论

当前七张表已经形成了基本分层：

```text
数据源层：data_source
    ↓
采集任务层：crawl_task
    ↓
原始公告层：raw_notice
    ↓
解析结果层：notice_extraction
    ↓
项目事实层：project + project_notice + project_requirement
```

主要结构问题集中在五个方向：

1. **原始公告身份和公告内容版本没有拆开**，同一公告发生内容变化时缺少完整版本结构。
2. **项目没有稳定唯一身份**，单个项目编号和项目名称不足以支持跨公告、跨标段归并。
3. **解析结果进入业务公告的关系不完整**，无法明确 `project_notice` 最终采用了哪一版抽取结果。
4. **原始层、解析层和事实层存在大量重复字段**，但没有定义哪张表是事实来源、哪张表是快照、哪张表允许修订。
5. **多个关键业务唯一性只依靠普通索引或代码逻辑**，数据库结构本身不能防止重复。

---

## 二、分层职责问题

建议七张表的职责明确为：

| 表 | 应承担的唯一职责 |
|---|---|
| `data_source` | 描述外部数据源的业务身份 |
| `crawl_task` | 描述一次具体、可重放的采集运行 |
| `raw_notice` | 保存源站公告身份和不可变原始版本 |
| `notice_extraction` | 保存某个解析器版本对原始公告的完整抽取结果 |
| `project` | 保存跨公告归并后的唯一项目主数据 |
| `project_notice` | 保存已经归属项目、被业务采用的标准公告 |
| `project_requirement` | 保存从标准公告拆出的资格、技术、业绩等要求 |

当前结构没有完全落实这一职责边界，主要表现为：

- `raw_notice` 同时承担公告身份、内容版本和任务归属；
- `notice_extraction.extracted_fields` 与 `project_notice.structured_data` 容易保存相同内容；
- `raw_notice.raw_text` 与 `project_notice.content` 重复；
- `project` 与 `project_notice.structured_data` 重复保存项目名称、行业、金额、地点等字段；
- `project_requirement` 没有精确指向产生它的抽取结果。

## 三、各表主要结构问题

## 3.1 `data_source`

### 主要问题一：业务数据源和爬虫实现没有分离

当前只有 `short_code`，容易同时承担：

- 业务数据源代码；
- Spider名称；
- 网站域名简码；
- 外部平台代码。

这些概念不一定一一对应。一个网站可能有多个业务模块和多个爬虫，一个爬虫也可能复用到多个相同技术平台。

### 主要问题二：采集配置和调度配置放在数据源主表

`crawl_frequency_minutes` 和 `crawl_config` 直接属于 `data_source`，隐含“一数据源一套爬虫、一种频率”的假设。

当一个数据源存在公告、采购、合同等多个采集模块时，当前结构无法为每个模块设置不同：

- Spider；
- 采集频率；
- 栏目范围；
- 增量策略；
- 启停状态；
- 配置版本。

### 主要问题三：数据源分类字段缺少标准约束

`source_level`、`province` 是自由字符串，容易产生不同名称口径。

### 建议方向

保留 `data_source` 作为数据源业务主表，新增爬虫配置表：

```text
data_source_crawler
- id
- data_source_id
- crawler_code
- module_type
- config_json
- config_version
- is_enabled
```

调度频率可继续拆到 `crawl_schedule`，避免把运行策略固化在数据源主表。

---

## 3.2 `crawl_task`

### 主要问题一：缺少任务运行配置快照

任务只关联 `data_source_id`，没有记录这次运行实际使用的：

- crawler/spider；
- 模块和栏目；
- 时间范围；
- 分页参数；
- 配置版本；
- Spider和解析器代码版本。

数据源配置发生变化后，历史任务不能从数据库结构中完整还原。

### 主要问题二：任务关系只能表达简单的一次运行

没有：

- 父任务；
- 子任务；
- 重试任务；
- 补采任务；
- 第几次尝试。

无法结构化表达大任务拆分和失败重试。

### 主要问题三：任务与公告是一对多单归属

`raw_notice.crawl_task_id` 只能让一条公告属于一个任务。但同一公告可能：

- 首次被某任务发现；
- 被后续任务再次看到；
- 在某次任务中发生内容变化。

单一外键不能表达“任务发现公告”的多对多关系。

### 主要问题四：状态和统计缺少数据库约束

`task_type`、`status` 都是自由字符串，数量字段也没有一致性CHECK约束。

### 建议方向

- 增加 `task_config JSON` 和 `config_version`；
- 增加 `crawler_version/parser_version`；
- 增加 `parent_task_id/retry_of_task_id/attempt_no`；
- 增加 `crawl_task_notice`，记录任务与公告的发现关系；
- 对任务时间和数量增加CHECK约束。

---

## 3.3 `raw_notice`

### 主要问题一：公告身份和公告版本混在一张表

当前唯一约束：

```text
UNIQUE(data_source_id, source_notice_id)
```

该设计只能保存源站公告的单一当前状态，无法自然保存：

- 同一公告的历史正文；
- 内容变更版本；
- 更正前后差异；
- 每个版本对应的任务和指纹。

### 主要问题二：`source_notice_id` 可空但参与唯一键

MySQL唯一索引允许多条NULL。没有稳定源站ID时，当前唯一约束不能防止重复公告。

### 主要问题三：原始内容载体不完整

当前只有：

```text
raw_html
raw_text
```

无法统一保存API JSON、XML、文件响应等非HTML原始内容。表名虽然是“原始公告”，却没有通用原始载荷字段。

### 主要问题四：缺少原始响应元数据

缺少：

- 原始响应格式；
- 响应URL；
- HTTP状态码；
- Content-Type；
- 原始响应哈希；
- 哈希算法。

### 主要问题五：源站分类信息没有保存

表中没有源站栏目、公告子类型、公告性质等字段。标准类型可以在解析层产生，但源站原始分类仍应在原始层保留。

### 主要问题六：`parse_status` 职责过重

抓取状态、内容完整性、字段抽取、项目归并是不同阶段，不应由一个状态字段共同表达。

### 建议方向

推荐拆分为：

```text
raw_notice_identity
- id
- data_source_id
- source_notice_id
- source_url
- first_seen_at
- last_seen_at

raw_notice_version
- id
- identity_id
- fingerprint
- raw_payload
- payload_format
- raw_text
- publish_date
- crawl_time
- UNIQUE(identity_id, fingerprint)
```

任务发现关系放入 `crawl_task_notice`，不再依赖 `raw_notice.crawl_task_id` 单一归属。

---

## 3.4 `notice_extraction`

### 主要问题一：缺少抽取版本唯一约束

建议的业务唯一键应为：

```text
UNIQUE(raw_notice_id, extraction_model, extraction_version)
```

当前结构无法从数据库层保证同一公告、同一模型和同一版本只有一条结果。

### 主要问题二：模型和版本字段可空

`extraction_model`、`extraction_version` 可空，会导致抽取结果无法稳定追踪、比较和去重。

### 主要问题三：抽取结果JSON缺少独立Schema版本

解析器版本和JSON结构版本是两个概念。解析器升级不一定改变Schema，Schema升级也不一定更换模型。

### 主要问题四：缺少“被业务采用的抽取版本”关系

同一原始公告可能有：

- 规则解析版本；
- AI解析版本；
- 人工修订版本。

当前 `project_notice_id` 只能说明抽取结果与业务公告有关，不能明确哪一条抽取结果最终生成了 `project_notice.structured_data`。

### 主要问题五：`extracted_fields` 与 `project_notice.structured_data` 职责重复

如果两个字段都保存相同JSON，会产生双份数据和版本漂移。

建议定义：

- `extracted_fields`：某次解析的完整、不可变输出；
- `project_notice.structured_data`：被采用并规范化后的业务字段。

### 主要问题六：审核和置信度约束不足

- `verified_by` 没有用户外键；
- `is_verified=true` 时不要求审核人和审核时间；
- 置信度没有0到1范围约束；
- 人工修订没有单独版本记录。

### 建议方向

- 模型、模型版本、Schema版本设为非空或明确标识；
- 增加版本唯一约束；
- 增加 `is_selected` 或由 `project_notice` 保存 `selected_extraction_id`；
- 人工审核和修订拆为独立记录；
- 对置信度增加CHECK约束。

---

## 3.5 `project`

### 主要问题一：没有稳定的项目唯一身份

当前只有：

```text
project_code
project_name
```

两者都不是可靠的单字段唯一键：

- 一个项目可能有多个交易编号、招标编号和标段编号；
- 同一项目在不同公告阶段名称可能变化；
- 相同名称可能属于不同年份、不同标段或不同采购人。

### 主要问题二：单个 `project_code` 无法表达多编号

将多个编号拼入一个字段会导致：

- 长度不可控；
- 无法按单个编号查询；
- 无法标记编号类型；
- 无法记录编号来自哪个数据源和公告。

### 主要问题三：缺少项目别名和来源标识

数据库无法保存项目在不同网站、不同公告阶段使用过的名称和编号。

### 主要问题四：项目主字段缺少来源和修订记录

`industry`、金额、地点、招标人等字段可能来自不同公告，但表中没有记录：

- 最终值来自哪条公告；
- 采用了什么合并规则；
- 是否经过人工确认；
- 历史值如何变化。

### 主要问题五：与公告结构字段重复

`project` 与 `project_notice.structured_data` 都会保存：

- 项目名称；
- 行业、类型；
- 金额；
- 地点；
- 招标人和代理机构；
- 开标时间等。

应明确：

- `project` 保存跨公告合并后的规范当前值；
- `project_notice` 保存单条公告发布时的字段快照。

### 主要问题六：部分字段类型不适合业务内容

- `project_code VARCHAR(191)` 不适合保存组合编号；
- `duration VARCHAR(191)` 不适合长工期描述；
- 金额缺少币种和原始单位；
- `province/city` 没有行政区划代码；
- `current_status VARCHAR(191)` 过宽且没有字典约束。

### 建议方向

增加：

```text
project_identifier
- project_id
- data_source_id
- identifier_type
- identifier_value
- normalized_value
- source_notice_id

project_alias
- project_id
- alias_name
- normalized_alias
- data_source_id
```

如需自动/人工归并，再增加 `project_match_candidate` 或合并审核表。

## 3.6 `project_notice`

### 主要问题一：缺少与原始公告的直接关系

表中没有 `raw_notice_id` 或公告身份外键，业务公告与原始公告的追溯依赖 `notice_extraction` 反向关系，不够稳定。

### 主要问题二：缺少数据源外键

只有 `source_site` 文本，没有 `data_source_id`。数据源名称被复制后可能发生改名漂移，也无法建立稳定的来源唯一键。

### 主要问题三：没有来源公告唯一约束

`source_notice_id` 只有普通索引，结构上不能防止同一来源公告重复进入业务层。

### 主要问题四：没有明确采用哪一版解析结果

`structured_data` 没有对应的 `selected_extraction_id`，无法证明业务结构字段来自哪个模型和版本。

### 主要问题五：与 `raw_notice` 重复保存公告字段

重复字段包括：

```text
title
content / raw_text
publish_date
source_url
source_notice_id
crawl_time
```

重复本身可以用于保存业务修订版本，但必须增加来源关系、版本和修订规则，否则两份值可能不一致。

### 主要问题六：与 `notice_extraction` 重复保存结构化JSON

`structured_data` 缺少Schema版本、审核状态和抽取来源。

### 主要问题七：字段定义跨层不一致

```text
raw_notice.source_notice_id      VARCHAR(256)
project_notice.source_notice_id  VARCHAR(191)

notice_extraction.notice_type    VARCHAR(64)
project_notice.notice_type       VARCHAR(191)
```

相同业务字段在不同层长度不一致，会增加转换和截断风险。

### 主要问题八：缺少待匹配公告的结构承接

`project_id` 非空是合理的事实层约束，但系统还需要独立的匹配候选表承接尚未确认项目归属的公告，不能只依靠放宽外键可空性。

### 建议方向

- 增加 `data_source_id`；
- 增加原始公告身份或版本外键；
- 增加来源公告唯一约束；
- 增加 `selected_extraction_id` 和结构Schema版本；
- 增加 `review_status/updated_at`；
- 统一跨层字段长度和公告类型代码。

---

## 3.7 `project_requirement`

### 主要问题一：来源追溯不够精确

只有 `project_id` 和 `notice_id`，没有 `extraction_id`，无法知道要求由哪次解析产生。

### 主要问题二：没有业务唯一约束

同一公告、同一类型、相同文本可以重复保存。

### 主要问题三：要求类型是自由字符串

资格、资质、人员、技术、业绩、财务等分类没有标准代码约束。

### 主要问题四：`is_mandatory` 表达能力不足

实际要求可能是：

- 必须满足；
- 否决条件；
- 优先条件；
- 加分条件；
- 一般描述；
- 无法判断。

单个布尔值无法表达这些差异。

### 主要问题五：只有文本和关键词，缺少可计算条件

无法结构化表达：

- 金额阈值；
- 资质名称和等级；
- 年限要求；
- 人员数量；
- 逻辑关系（AND/OR）；
- 有效期。

### 主要问题六：缺少原文定位

没有正文片段、段落位置或页码，无法追溯要求在原文中的证据。

### 建议方向

- 增加 `extraction_id`；
- 增加要求内容指纹和唯一约束；
- 将 `is_mandatory` 扩展为 `requirement_level/rule_type`；
- 增加 `condition_json` 和Schema版本；
- 增加 `source_snippet/source_offset/page_no`。

## 四、七张表之间的重复字段问题

| 重复内容 | 涉及表 | 核心问题 | 建议边界 |
|---|---|---|---|
| 公告标题、正文、发布时间、URL | `raw_notice`、`project_notice` | 原始值与业务值无来源关系 | raw保存不可变原始版本，project_notice保存业务采用版本 |
| 公告结构化字段 | `notice_extraction`、`project_notice` | 无法判断采用哪次抽取 | extraction保存完整版本输出，project_notice保存被选中的标准结果 |
| 项目名称、行业、金额、地点 | `project`、`project_notice.structured_data` | 主数据与公告快照边界不清 | project保存跨公告规范值，notice保存公告时点值 |
| 公告类型 | `raw_notice`缺失、`notice_extraction`、`project_notice` | 源站类型与标准类型未分离 | raw保存源站分类，后两表保存统一标准代码 |
| 数据源信息 | `data_source`、`raw_notice.data_source_id`、`project_notice.source_site` | 业务层复制名称却无外键 | 各层使用data_source_id，名称仅作展示快照 |
| 项目要求文本 | `notice_extraction.extracted_fields`、`project_requirement` | 拆分后缺少来源 | requirement关联extraction并保存证据位置 |

## 五、关键关系缺失

当前结构最需要补齐的关系如下：

```text
data_source
    └── data_source_crawler / crawl_schedule

crawl_task
    └── crawl_task_notice

raw_notice_identity
    └── raw_notice_version
            └── notice_extraction

notice_extraction
    └── selected/adopted relationship
            └── project_notice

project
    ├── project_identifier
    ├── project_alias
    └── project_notice

project_requirement
    └── notice_extraction + source evidence
```

## 六、整改优先级

### P0：决定主数据和版本模型

- [ ] 拆分原始公告身份与内容版本；
- [ ] 增加通用原始载荷字段；
- [ ] 建立任务与公告多对多关系；
- [ ] 建立项目多编号和别名结构；
- [ ] 建立项目匹配候选/审核结构；
- [ ] 为 `project_notice` 增加数据源和原始公告外键；
- [ ] 明确业务公告采用的抽取版本。

### P1：增加数据库级约束

- [ ] 抽取结果增加版本唯一键；
- [ ] 项目公告增加来源唯一键；
- [ ] 项目要求增加内容唯一键；
- [ ] 状态、类型、置信度和任务数量增加CHECK或字典约束；
- [ ] 参与唯一键的关键字段尽量改为非空。

### P2：统一重复字段和字段标准

- [ ] 明确原始值、解析值、业务值的唯一所有者；
- [ ] 统一公告ID、公告类型等跨层字段长度；
- [ ] 为JSON增加Schema版本；
- [ ] 统一时间时区、金额币种和行政区划代码；
- [ ] 为项目和要求字段增加来源与修订审计。

---

## 七、建议优先评审的五项结构变更

1. `raw_notice_identity + raw_notice_version`；
2. `crawl_task_notice`；
3. `project_identifier + project_alias + project_match_candidate`；
4. `project_notice` 到数据源、原始公告和选中抽取版本的关系；
5. `project_requirement` 到抽取结果和原文证据的关系。

这五项是七张核心表能否形成清晰、可追溯、可扩展数据库结构的基础。
