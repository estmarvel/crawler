# 爬虫数据处理漏斗与入库流水线说明

> **已过时（2026-07-27）：** 本文的六阶段表和幂等设计仍有历史参考价值，但其状态集缺少 `PARTIAL_SUCCESS`、漏斗单调不等式不适用于部分解析、直接累加阶段行的口径已改为重试链合并，数量也是历史快照。当前流水线以《数据库修改与接口变更汇总说明》为准。

## 1. 当前实现范围

本轮已经把华新、玖邦采集任务接入六阶段处理流水线：

```text
采集抓取 → 解析提取 → 去重清洗 → 结构化存储 → 智能匹配 → 推荐输出
```

当前明确不写入 `project_requirement`。推荐算法也不在爬虫任务中执行，因此“推荐输出”阶段真实记录为 `SKIPPED`，成功数量为 0，不使用项目总数伪造推荐数量。

原始 JSON、附件和 `task.log` 继续作为可回放归档保留。Scrapy 不直接操作业务表；API 负责任务生命周期，Node 导入器负责幂等入库和项目关联。

## 2. 六阶段与数据库对应关系

| 阶段代码 | 前端名称 | 主要处理 | 成功数量口径 |
| --- | --- | --- | --- |
| `FETCH` | 采集抓取 | 运行 Scrapy、校验 JSON 文件、生成 `manifest.json` | JSON 中公告总数 |
| `PARSE` | 解析提取 | 写入/更新原始公告、原始附件和公告抽取结果 | 存在抽取结果的本任务公告数 |
| `DEDUPLICATE` | 去重清洗 | 按数据源与公告 ID 去重，记录本次任务发现关系 | 本任务唯一公告数 |
| `STORE` | 结构化存储 | 确认 `raw_notice`、附件和 `notice_extraction` 完整落库 | 原始层和抽取层入库成功公告数 |
| `MATCH` | 智能匹配 | 增量刷新 `project`，写入/更新 `project_notice` 和业务附件，回填抽取关系 | 成功关联 `project_notice` 的公告数 |
| `RECOMMEND` | 推荐输出 | 当前不执行推荐，也不写 `project_requirement` | 固定为 0，阶段状态为 `SKIPPED` |

漏斗接口从 `crawl_task_stage.success_count` 聚合，不再用不同业务表的全库行数拼凑。正常情况下满足：

```text
FETCH ≥ PARSE ≥ DEDUPLICATE ≥ STORE ≥ MATCH ≥ RECOMMEND
```

### 2.1 各阶段实际处理逻辑

1. `FETCH`：API 根据前端提交的采集源、采集类型、栏目、时间范围和可选数量限制启动原 Scrapy 代码；爬虫输出 JSON 和附件后，API 校验每个 JSON 顶层是数组，计算文件大小及 SHA-256，并生成 `manifest.json`。此阶段不直接写公告业务表。
2. `PARSE`：依次运行 `raw_notice`、`raw_notice_attachment`、`notice_extraction` 导入器。原始公告按 `(data_source_id, source_notice_id)` 幂等写入；正文、发布时间、附件和表格要求的抽取字段在这里落库。
3. `DEDUPLICATE`：通过 `crawl_task_notice` 保存“本任务发现了哪条公告”，并区分 `is_new`、`is_updated` 和未变化公告。重复采集不会复制 `raw_notice`，但会保留本次任务发现关系。
4. `STORE`：检查本任务唯一公告中有多少已经具备抽取结果，用于确认原始层、附件层和抽取层完整落库。它是入库完整性阶段，不会再次复制数据。
5. `MATCH`：执行项目身份匹配，增量写入/更新 `project`、`project_notice`、`project_notice_attachment`，并回填 `notice_extraction.project_notice_id`。项目编号优先；无编号公告按既定的名称和标段归一规则匹配。`project_requirement` 当前明确不写入。
6. `RECOMMEND`：当前爬虫流水线不执行企业推荐，因此阶段状态为 `SKIPPED`、成功数为 0、跳过数为匹配公告数。以后真正接入推荐算法后才应写成功数量。

任一阶段失败时，该阶段记为 `FAILED` 并写入 `crawl_exception`；已经提交的前序数据保留，后续阶段不再执行。修复原因后从异常页重试会创建一个新任务，不会覆盖旧任务审计记录。

补充：`raw_notice.parse_status=PARSED` 只表示原始公告 JSON 已成功进入原始层，不等价于已生成 `notice_extraction`。漏斗“解析提取”以任务阶段和抽取结果为准；若原始公告导入完成后任务超时，可能出现原始公告存在但解析提取阶段失败的情况。

## 3. 新增运行表

### 3.1 `crawl_task_stage`

每个任务预建六条阶段记录，前端漏斗、任务详情、异常定位共用这些数据。

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `id` | `BIGINT` | 阶段记录主键 |
| `crawl_task_id` | `BIGINT` | 所属任务，删除任务时级联删除 |
| `stage` | `VARCHAR(32)` | `FETCH/PARSE/DEDUPLICATE/STORE/MATCH/RECOMMEND` |
| `status` | `VARCHAR(32)` | `PENDING/RUNNING/SUCCESS/FAILED/SKIPPED/CANCELLED` |
| `input_count` | `INT` | 进入该阶段的数量 |
| `success_count` | `INT` | 阶段成功数量 |
| `skipped_count` | `INT` | 重复、无法匹配或按范围主动跳过数量 |
| `failed_count` | `INT` | 阶段失败数量 |
| `error_message` | `TEXT` | 阶段失败原因 |
| `metadata` | `JSON` | 清单路径、新增/更新/未变化数量、映射目录等扩展信息 |
| `started_at/finished_at` | `DATETIME(3)` | 阶段起止时间 |
| `created_at/updated_at` | `DATETIME(3)` | 审计时间 |

唯一键为 `(crawl_task_id, stage)`，同一任务同一阶段只能有一条记录。

### 3.2 `crawl_task_notice`

用于表达“某次任务发现过某条原始公告”，解决 `raw_notice.crawl_task_id` 被后续任务覆盖导致历史统计变化的问题。

| 字段 | 类型 | 作用 |
| --- | --- | --- |
| `id` | `BIGINT` | 主键 |
| `crawl_task_id` | `BIGINT` | 本次采集任务 |
| `raw_notice_id` | `BIGINT` | 唯一原始公告 |
| `is_new` | `BOOLEAN` | 该任务是否首次发现公告 |
| `is_updated` | `BOOLEAN` | 已有公告内容是否发生变化 |
| `content_hash` | `VARCHAR(64)` | 本次内容指纹 |
| `discovered_at` | `DATETIME(3)` | 本次发现时间 |

唯一键为 `(crawl_task_id, raw_notice_id)`。同一 JSON 或同一任务重复回放不会产生重复关系。

## 4. 幂等与唯一约束

本轮增加以下数据库唯一约束：

- `project.project_code`：非空项目编号只能对应一个项目；MySQL 仍允许多个 `NULL`，用于无编号计划项目。
- `project_notice(source_site, source_notice_id)`：同一平台公告只保存一份业务公告。
- `notice_extraction(raw_notice_id, extraction_model, extraction_version)`：同一原始公告同一抽取版本只保存一份结果。

原始公告导入的变化：

- `raw_notice` 仍按 `(data_source_id, source_notice_id)` Upsert；
- 已有公告更新内容时不再覆盖原始 `crawl_task_id`；
- 每次发现情况写入 `crawl_task_notice`；
- JSON 批次内部重复公告、重复附件、重复抽取结果保留最后一条并统计跳过数量，不再让整批失败。

## 5. 项目与公告增量处理

`import_projects.js` 每次使用完整公告链重新计算项目字段和 `current_status`：

- 已有项目按项目编号或标准化独立项目名称更新，保留原 `project.id`；
- 新项目追加插入，不清空项目表、不重置自增 ID；
- 项目编号、招标编号、标准化项目名和标段归一化规则继续沿用现有实现；
- 未匹配招标计划可建立 `project_code=NULL` 的独立计划项目；
- 低可信且有冲突的公告保留抽取结果，进入人工复核，不强行关联。

`import_project_notices.js` 的变化：

- 已有公告仅在项目、正文、结构化字段、时间或来源发生变化时更新；
- 新公告增量插入；
- 只更新发生变化的 `notice_extraction.project_notice_id`；
- 不使用 `--replace`，避免破坏附件和其他业务外键。

`import_project_notice_attachments.js` 按父公告与文件哈希/路径/URL/名称复用已有附件；没有附件时正常返回成功。

## 7. 任务、事件和异常

任务创建、六条阶段记录和 `CREATED` 事件在同一数据库事务中完成。

阶段运行会产生：

- `{STAGE}_STARTED`
- `{STAGE}_COMPLETED`
- `{STAGE}_FAILED`
- `PROJECT_REQUIREMENT_SKIPPED`

阶段失败写入 `crawl_exception`：

- `source_type=CRAWL_STAGE`
- `source_ref={crawlTaskId}:{stage}`
- `exception_type` 为代理、超时或 `{STAGE}_FAILED` 等分类

定时计划无法派发时写入：

- `source_type=CRAWL_SCHEDULE`
- `exception_type=SCHEDULE_DISPATCH`

调度失败不会提前推进 `next_run_at`，调度器会在数据源空闲后再次尝试。成功派发后对应计划异常自动解决。

异常重试的任务创建、六阶段初始化、事件写入和异常改为 `PROCESSING` 在同一事务内完成。重复点击正在处理的异常返回 HTTP 409。重试成功自动把原异常改为 `RESOLVED`；失败或取消则恢复为 `OPEN` 并记录重试任务结果。

## 8. 接口变化

现有路径不变：

- `POST /api/admin/crawler/tasks`
- `GET /api/admin/crawler/tasks`
- `GET /api/admin/crawler/tasks/:id`
- `GET /api/admin/crawler/tasks/:id/logs`
- `GET /api/admin/crawler/tasks/:id/logs/stream`
- `POST /api/admin/crawler/exceptions/:id/retry`
- `GET /api/admin/collection`
- `GET /api/admin/overview`

`GET /api/admin/exceptions` 是管理概览的只读聚合接口，其条目 ID 可能是 `task:5` 等复合标识；持久化异常的更新和重试只使用 `/api/admin/crawler/exceptions/:id`，不再提供容易混淆的写操作兼容别名。

任务查询对象新增 `stages`：

```json
{
  "stages": [
    {
      "id": "61",
      "crawlTaskId": "11",
      "stage": "FETCH",
      "status": "SUCCESS",
      "inputCount": 20,
      "successCount": 20,
      "skippedCount": 0,
      "failedCount": 0,
      "errorMessage": null,
      "metadata": {},
      "startedAt": "2026-07-24T10:00:00.000Z",
      "finishedAt": "2026-07-24T10:01:00.000Z"
    }
  ]
}
```

SSE 新增 `stage` 事件，原 `status`、`log` 事件保持不变。阶段结束时管理端重新读取 `/api/admin/collection`，更新真实漏斗数据，不改变页面布局或图表样式。
