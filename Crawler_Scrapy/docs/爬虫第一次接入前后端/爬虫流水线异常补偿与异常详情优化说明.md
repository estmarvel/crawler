# 爬虫流水线异常补偿与异常详情优化说明

> **已归并（2026-07-27）：** 本文的检查点、分阶段超时、自动补偿、异常详情和历史修复结果已分别合并到当前主文档和 2026-07-24 历史核验报告。需特别注意：当前补偿复用 JSON 后从 `PARSE` 重新校验并顺序执行下游，`resumeFromStage` 记录原故障点，不代表运行器会直接跳到该阶段。

## 一、优化目标

解决采集任务已经获得 JSON 或已经写入 `raw_notice`，但因为解析超时、API 重启或下游导入异常，导致 `notice_extraction`、`project_notice` 缺失的问题。

本次采用“保留成功检查点、失败阶段续跑”的方式，不对完整任务做全局回滚，也不因为解析失败重新请求源站。

## 二、优化后的处理流程

```text
源站采集
  → JSON及manifest校验
  → raw_notice/crawl_task_notice
  → notice_extraction
  → project/project_notice
  → project_notice_attachment
```

- 抓取进程异常退出，但任务目录中存在有效 JSON：将 `FETCH` 标记为 `PARTIAL_SUCCESS`，保留 JSON 并继续下游导入。
- 原始公告导入后：`raw_notice.parse_status` 临时设为 `PENDING`。
- 提取成功：设为 `PARSED`。
- 提取失败：设为 `RETRY_PENDING`，并以具体 `raw_notice.id` 写入 `crawl_exception`。
- 下游异常重试：在新任务的 `run_config` 中记录 `resumeFromTaskId` 和 `resumeFromStage`，复用原任务 JSON，不再请求网站。
- 自动补偿：每分钟扫描一次可恢复异常，按 1、5、30 分钟退避，最多自动重试 3 次。
- API重启：保留当前检查点，并把正在执行的阶段登记为 `API_RESTART_INTERRUPTED`，后续从阶段检查点恢复。
- 范围化补偿：通过 `crawl_task_notice.raw_notice_id` 限定本次补偿范围。项目身份判断仍读取完整公告链，保证项目状态准确，但只更新受影响项目、项目公告和附件，不再因少量失败全库重写。

项目匹配完成后会再次校验本任务公告：

- 已有 `notice_extraction.project_notice_id`：计入 `MATCH.success_count`。
- 已生成 `notice_extraction` 但没有关联项目公告：`MATCH` 标记为 `PARTIAL_SUCCESS`，并生成 `MATCH_INCOMPLETE` 异常。
- 任务最终的 `success_count` 表示完整通过 `MATCH` 的公告数，`fail_count` 表示尚未走完整条流水线的公告数。
- 补偿任务只有在 `fail_count=0` 时才解决原异常；部分成功会将原异常重新置为 `OPEN`，避免遗漏。

## 三、阶段超时

原来的 `timeoutMinutes` 覆盖从抓取到项目匹配的全部时间，可能出现抓取已经结束、解析刚开始便被总计时器终止的问题。

现在改为单阶段计时：

| 阶段 | 超时规则 |
| --- | --- |
| `FETCH` | 使用任务填写的 `timeoutMinutes` |
| `PARSE`、`DEDUPLICATE`、`STORE` | 至少 10 分钟，每进入一个阶段重新计时 |
| `MATCH` | 至少 30 分钟，进入阶段重新计时 |

一个阶段完成后会清除该阶段计时器，不会继续消耗后续阶段的运行时间。

## 四、异常详情接口

### 请求

```http
GET /api/admin/crawler/exceptions/:id
```

### 返回内容

- 异常基础信息：类型、状态、消息、重试次数、关联标识。
- 问题诊断：失败阶段、可能原因、具体错误、建议处理。
- 恢复方式：`RESUME_FROM_JSON` 或 `REFETCH`。
- 关联任务：任务类型、状态、数量、时间、运行参数、JSON目录、日志文件。
- 流水线阶段：每个阶段的输入、成功、跳过、失败数量和错误。
- 受影响公告：`raw_notice.id`、源站公告ID、标题、详情链接、解析状态、提取数量、项目公告ID。
- 最近任务事件：来自 `crawl_task_event`。
- 重试历史：重试任务ID、状态和执行时间。

异常详情是通过已有表动态汇总得到的，没有为重复信息新增数据库字段：

```text
crawl_exception
  + crawl_task
  + crawl_task_stage
  + crawl_task_event
  + crawl_task_notice
  + raw_notice
  + notice_extraction
  + project_notice
```

## 五、异常中心展示

管理端“异常处理 → 查看详情”现在可以查看：

1. 具体失败阶段和错误原因。
2. 建议处理方法和自动重试时间。
3. 是否会复用 JSON，是否需要重新访问网站。
4. 完整任务参数、输出目录和日志路径。
5. 各阶段实际数量。
6. 受影响公告及源站详情链接。
7. 任务事件与重试任务历史。

已解决、已忽略或达到三次自动重试上限的异常，详情中的“下次重试”显示“无待执行自动重试”，不再显示错误的退避时间。

## 六、范围化导入参数

补偿任务调用导入脚本时使用以下限定参数：

| 脚本 | 限定参数 | 作用 |
| --- | --- | --- |
| `import_projects.js` | `--raw-notice-ids=...` | 全链计算身份和状态，只写受影响项目及映射 |
| `import_project_notices.js` | `--site=huaxin\|jiubang` | 只读取本次站点的映射文件 |
| `import_project_notice_attachments.js` | `--raw-notice-ids=...` | 只写本任务公告的项目附件 |

所有范围参数都禁止与 `--replace` 同时使用，防止把全表删除后只恢复局部数据。

## 九、数据处理漏斗的补偿统计口径

漏斗不再直接累加所有 `crawl_task_stage.success_count`。原任务和它创建的重试任务会先按 `run_config.retryOfTaskId` 合并为一次逻辑采集，再对每个阶段取该采集链中的最大成功数。

这样，补偿任务复用原任务 JSON 时不会把同一批公告重复计入“采集抓取”，但补偿后完成的解析、存储和匹配仍会反映在漏斗中。独立的手工任务和定时任务仍分别统计。
