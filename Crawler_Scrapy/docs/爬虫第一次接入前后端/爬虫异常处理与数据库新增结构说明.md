## 1. 本次调整结论

管理端“新建采集任务”和“新建定时任务”必须选择采集栏目；增量任务必须填写回溯天数，指定范围任务必须填写开始日期。每页数量、每栏目最大公告数、最大页数和超时分钟改为可选，未填写表示采集完整时间范围，不再要求用户为了按天回溯而额外设置数量限制。

接口也不再把用户输入二次截断为“每栏目 20 条、最多 2 页、最长 60 分钟”。当前校验范围为：

| 参数 | 含义 | 接口范围 | 是否必填 |
| --- | --- | --- | --- |
| `sections` | 采集栏目数组 | 至少 1 个，最多 4 个 | 是 |
| `pageSize` | 目标站点列表接口每页请求数量 | `1～100` | 否；默认 100 |
| `maxRecords` | 每个栏目最多处理的公告数量 | `1～1,000,000` | 否；默认 1,000,000，等效于不主动限制 |
| `maxPages` | 每个栏目最多翻页数 | `1～100,000` | 否；默认 10,000，通常由源站最后一页自然结束 |
| `timeoutMinutes` | API 管理该任务的最长运行时间 | `1～10,080` 分钟 | 否；默认 720 |
| `lookbackDays` | 增量采集回溯天数 | `1～3,650` 天 | `INCREMENTAL` 必填 |
| `startDate` | 指定范围采集开始日期 | `YYYY-MM-DD` | `HISTORY_RANGE` 必填 |
| `endDate` | 指定范围采集结束日期 | `YYYY-MM-DD`，不得早于开始日期 | 否 |
| `importData` | 爬取成功后是否导入数据库 | 布尔值 | 否；当前前端固定传 `true` |

说明：所谓“默认爬全”是指不按记录数或页数提前截断所选时间范围，仍会遵守服务器直连的低并发、随机延迟、403/429 主动关停和单次响应安全预算，不会为了追求全量而移除防封保护。

独立“数据来源”页的“同步”和“测试连接”按钮仍会主动提交一组明确的小范围参数。这些是按钮自身操作的固定参数，不是 API 默认值，也不会影响采集中心“新建采集任务”的输入。

## 2. 前端新建任务与接口参数对应

### 2.1 新建采集任务

页面位置：管理端“采集中心” → “采集任务管理” → “新建采集任务”。“采集任务管理”读取的是真实 `crawl_task`，不再用 `crawl_schedule` 计划记录冒充任务记录；列表展示任务 ID、采集源、采集类型、执行方式、状态、计划时间、开始时间和采集结果，并按任务状态提供相应操作。

任务表调用 `GET /api/admin/crawler/tasks?page=N&pageSize=10` 做服务端分页，每页最多显示 10 条，分页总数使用接口返回的 `total`，不是把前端已加载的数据再切片。

操作列按照任务状态只显示当前有效的一个操作：

| `crawl_task.status` | 页面按钮 | 实际行为 |
| --- | --- | --- |
| `RUNNING` | 停止 | 直接调用停止接口安全结束进程，任务最终进入 `CANCELLED` |
| `CANCELLED` | 启用 | 保留原任务并复制 `run_config`；原预约时间仍在未来时继续预约，已过期时提示后改为立即执行 |
| `FAILED`、`TIMED_OUT`、`PARTIAL_SUCCESS` | 重试 | 保留原任务并复制原参数；预约时间处理规则同上 |
| `PENDING` | 取消 | 不弹确认框，直接取消尚未启动的立即/预约任务；页面显示“已取消” |
| `CANCEL_REQUESTED` | 停止中 | 只显示禁用状态，等待进程安全退出 |
| `SUCCESS` | 再次执行 | 保留成功历史并复制原参数；预约时间处理规则同上 |

`crawl_task` 是一次运行记录，因此启用、重试和再次执行都会生成新 ID，原记录用于历史追溯。取消、启用、停止、重试和再次执行通常直接调用接口，不显示二次确认；仅当复制的预约时间已经过去时弹出提示，关闭提示后创建立即执行任务。

| 前端字段 | API 字段 | 写入位置/运行作用 |
| --- | --- | --- |
| 数据源 | `dataSourceId` | `crawl_task.data_source_id`；当前仅支持 `6=huaxin`、`14=jiubang` |
| 任务类型 | `taskType` | `crawl_task.task_type` |
| 执行方式 | 是否提交 `scheduledAt` | 选择“立即执行”时不提交；选择“预约执行”时必须选择未来时间 |
| 预约时间 | `scheduledAt` | `crawl_task.scheduled_at`；未来时间由调度器启动 |
| 回溯天数 | `options.lookbackDays` | 写入 `run_config`；增量任务转成脚本 `--days` |
| 开始/结束日期 | `options.startDate/endDate` | 写入 `run_config`；范围任务转成 `--start-date/--end-date` |
| 采集栏目 | `options.sections` | 写入 `run_config`；转成脚本 `--sections` |
| 每页数量 | `options.pageSize` | 可选；未填使用 100，写入 `run_config` 并转成 `--page-size` |
| 每栏目公告数 | `options.maxRecords` | 可选；未填使用 1,000,000，不主动截断通常规模的数据 |
| 最大页数 | `options.maxPages` | 可选；未填使用 10,000，正常由源站最后一页结束 |
| 超时分钟 | `options.timeoutMinutes` | 可选；未填使用 720，由 API 超时计时器执行终止 |
| 导入真实库 | `options.importData=true` | 爬取成功后依次执行 RawNotice、附件和抽取结果导入脚本 |

栏目代码：`zbgg_zys=招标公告`、`hxr=候选人公示`、`gs=中标结果`、`zbjh=招标计划`。

任务类型：

| 类型 | 用途 | 日期规则 |
| --- | --- | --- |
| `INCREMENTAL` | 按最近若干天采集 | 必须传 `lookbackDays` |
| `HISTORY_RANGE` | 按指定日期范围采集 | 必须传 `startDate`，`endDate` 可选 |
| `HISTORY_FULL` | 全历史采集 | 忽略回溯天数和日期范围 |

### 2.2 定时计划

页面位置：管理端“采集中心” → “定时计划管理”。它与上方的单次“采集任务管理”分开：只有需要按固定间隔重复运行时才创建计划。

定时计划也允许选择 `INCREMENTAL`、`HISTORY_RANGE`、`HISTORY_FULL` 三种采集类型。前端以“数值 + 分钟/小时/天”设置固定频率并换算为 `crawl_schedule.interval_minutes`；新建计划时修改频率会自动将下次执行时间更新为“当前时间 + 固定频率”，编辑已有计划时不会自动覆盖原下次执行时间。数量限制字段同样可选。计划保存到 `crawl_schedule`；调度器每 15 秒检查 `next_run_at`，每次到期都创建一条新的 `crawl_task`，不会复用旧任务记录。

### 2.3 采集源管理

采集源表改为读取全部 `data_source`，包括 `is_enabled=0` 的记录，并通过服务端分页每页显示 10 条。服务端按 `is_enabled DESC, id ASC` 排序，确保已启用数据源跨页稳定排在最前面。页面增加“是否启用”列；运行状态使用采集中绿色、空闲灰色、未启用红色；操作列只保留“编辑”。新增和编辑表单对应 `name`、`short_code`、`base_url`、`source_level`、`province`、`crawl_frequency_minutes`、`crawl_config`、`is_enabled`。

新建采集源会真实插入 `data_source`，编辑会更新对应记录。当前只有 ID 6（huaxin）和 ID 14（jiubang）已有爬虫实现；其他数据源可以维护配置，但不会出现在“新建采集任务”的可选列表，避免错误地启动不存在的 Spider。

任务与计划的边界：

| 用户目的 | 应使用的功能 | 数据库存储 |
| --- | --- | --- |
| 现在爬一次 | 新建采集任务 → 立即执行 | 一条 `crawl_task` |
| 未来某个时间只爬一次 | 新建采集任务 → 预约执行 | 一条 `crawl_task` |
| 每隔固定时间重复爬取 | 新建定时计划 | 一条 `crawl_schedule`；每次运行再生成一条 `crawl_task` |

## 3. 异常处理完整数据流

```text
前端创建任务
  → crawl_task(PENDING) + crawl_task_event(CREATED)
  → API 启动 Crawler_Scrapy/run_tws_history.sh
  → crawl_task(RUNNING) + crawl_task_event(STARTED)
  → 正常结束：crawl_task(SUCCESS) + crawl_task_event(COMPLETED)
  → 异常结束：crawl_task(FAILED/TIMED_OUT) + crawl_exception(OPEN)
                + crawl_task_event(FAILED/TIMED_OUT)
  → 管理端异常处理：查看 / 重试 / 忽略 / 标记已解决
```

### 3.1 异常识别规则

API 根据爬虫进程退出状态和最近日志内容分类：

| `crawl_exception.exception_type` | 触发条件 | 当前处理 |
| --- | --- | --- |
| `PROXY_AUTHENTICATION` | HTTP 407、`Proxy Authentication Required`、固定代理认证失败 | 任务失败，提示更新代理凭据或切换出口模式 |
| `PROXY_CONFIGURATION` | 固定代理或天启代理所需配置缺失 | 任务安全终止，不自动降级为未授权出口 |
| `PROXY_UNAVAILABLE` | 代理连接失败、代理池为空、CONNECT 隧道失败 | 任务失败并记录代理不可用 |
| `ACCESS_BLOCKED` | 服务器直连时命中 `direct_access_blocked`，通常为连续 403/429 | 防封保护主动停止任务并记录异常 |
| `TASK_TIMEOUT` | 超过该任务自己提交的 `timeoutMinutes` | 向整个受管进程组发送 `SIGTERM`，任务状态改为 `TIMED_OUT` |
| `TASK_EXECUTION` | 其他非零退出、导入脚本失败或未分类运行错误 | 记录通用任务执行异常 |
| `OUTPUT_DIRECTORY_FAILED` | API 无法创建任务输出目录 | 任务在启动爬虫前失败，检查目录权限、磁盘和挂载状态 |
| `FETCH_FAILED` | 采集阶段发生未归入代理/访问限制的异常，如输出 JSON 校验失败 | `FETCH` 阶段失败，后续阶段不执行 |
| `PARSE_FAILED` | 原始公告、附件或抽取结果导入器执行失败 | `PARSE` 阶段失败，保留 JSON 供修复后重试 |
| `DEDUPLICATE_FAILED` | `crawl_task_notice` 去重关系或统计发生异常 | `DEDUPLICATE` 阶段失败，停止后续存储确认 |
| `STORE_FAILED` | 原始层和抽取层完整性统计发生异常 | `STORE` 阶段失败，不继续项目匹配 |
| `MATCH_FAILED` | 项目、项目公告或业务附件导入和关联失败 | `MATCH` 阶段失败，已完成的原始层数据保留 |
| `RECOMMEND_FAILED` | 推荐阶段异常的预留分类 | 当前推荐阶段固定跳过，不会由正常运行主动产生 |
| `SCHEDULE_DISPATCH` | 到期定时计划无法创建采集任务 | 记录计划异常，不提前推进 `next_run_at`，后续轮询继续尝试 |

服务器直连防封由 `Crawler_Scrapy` 实现：单并发、每域名单并发、随机下载延迟、AutoThrottle、关闭普通重试，并在直连出口出现限制响应时由访问保护器快速关停。API 负责启动、超时、停止、分类和持久化，不另写一套爬取逻辑。

### 3.2 失败持久化规则

任务失败或超时时，API 在一个事务中执行：

1. 更新 `crawl_task.status`、`finished_at`、`fail_count`、`error_message`，并清空 `process_pid`。
2. 按 `(source_type, source_ref, exception_type)` 唯一键新增或更新 `crawl_exception`。
3. 将异常状态设为 `OPEN`，旧的 `resolved_at` 清空。
4. 新增一条 `crawl_task_event`，事件类型为 `FAILED` 或 `TIMED_OUT`。
5. 通过 SSE 向正在查看实时日志的前端发送最终状态。

当前任务异常使用：`source_type=CRAWL_TASK`，`source_ref=任务ID字符串`。同一任务的同一种异常只保留一条并更新；同一任务出现不同异常类型可以保留多条。

阶段异常使用 `source_type=CRAWL_STAGE`、`source_ref={任务ID}:{阶段代码}`；定时派发异常使用 `source_type=CRAWL_SCHEDULE`。前端已经为以上 14 类代码提供中文名称和严重程度颜色，不再直接显示英文代码。

### 3.2.1 前端演示异常

为验证异常页，项目提供可重复执行的模拟脚本：

```bash
cd /home/intsig/ProjectRecommendationSystem/api
npm run demo:exceptions -- --commit
```

脚本会先清理旧的模拟记录，再生成 13 个失败/超时任务和 14 条 `OPEN` 异常，覆盖上表所有类型。所有模拟任务的 `crawl_task.error_message`、异常消息和备注都带 `[DEMO_EXCEPTION]` 标识；阶段成功数均为 0，因此不会抬高漏斗成功数量。

清理命令：

```bash

```

该清理只删除带模拟标识的数据，不会删除真实任务和真实异常。

API 重启时会恢复数据库状态：遗留的 `RUNNING` 任务转成 `FAILED` 并生成异常；遗留的 `CANCEL_REQUESTED` 任务转成 `CANCELLED`，不生成异常。

### 3.3 异常状态

| 状态 | 前端文字 | 含义 |
| --- | --- | --- |
| `OPEN` | 待处理 | 新异常或异常再次发生，等待处理 |
| `PROCESSING` | 处理中 | 已从异常记录创建重试任务 |
| `RESOLVED` | 已解决 | 管理员确认问题已经解决 |
| `IGNORED` | 已忽略 | 管理员确认无需继续处理 |

变为 `RESOLVED` 或 `IGNORED` 时写入 `resolved_at`；改回 `OPEN` 或 `PROCESSING` 时清空 `resolved_at`。

### 3.4 前端按钮与接口

页面位置：管理端“异常处理”。所有成功响应统一为：

```json
{
  "code": 0,
  "data": {},
  "message": "ok"
}
```

| 页面动作 | 方法与路径 | 入参 | 数据库影响 |
| --- | --- | --- | --- |
| 加载异常列表和统计 | `GET /api/admin/crawler/exceptions` | `status?`、`page`、`pageSize` | 只读 `crawl_exception`，关联 `data_source.name` |
| 查看详情 | 无单独接口 | 使用列表行已有数据 | 无数据库写入 |
| 重试 | `POST /api/admin/crawler/exceptions/:id/retry` | 路径参数为异常 ID | 原异常改为 `PROCESSING`、`retry_count+1`；复制原 `run_config` 新建一个 `crawl_task` |
| 忽略 | `PATCH /api/admin/crawler/exceptions/:id` | `status=IGNORED`、`handledBy`、`remark` | 更新处理状态、处理人、备注和解决时间 |
| 标记已解决 | 同上 | `status=RESOLVED`、`handledBy`、`remark` | 更新处理状态、处理人、备注和解决时间 |

兼容路径 `PATCH/POST /api/admin/exceptions/:id...` 也指向同一处理逻辑；新前端统一使用 `/api/admin/crawler/exceptions`。

重试不会覆盖原 `crawl_task`。新任务的 `run_config.trigger=RETRY`，`run_config.retryOfTaskId=原任务ID`，便于追溯。

### 3.6 当前已知边界

以下是当前真实实现的边界，不能当成已经完成的能力：

1. `crawl_exception` 当前只持久化“爬虫任务级异常”。`raw_notice.parse_status` 失败、原始附件下载错误和项目附件错误仍由旧监控接口动态汇总，没有写入 `crawl_exception`，因此不能在新异常页执行状态流转或重试。
2. 管理端还有旧的 `GET /api/admin/exceptions` 监控接口，它动态读取多个业务表；新“异常处理”页读取的是 `GET /api/admin/crawler/exceptions`。两者统计口径不同。
3. 重试任务成功后，原异常不会自动从 `PROCESSING` 变成 `RESOLVED`；目前需要管理员确认后点击“标记已解决”。重试失败会按新任务 ID 生成新的异常，原异常可能继续停留在 `PROCESSING`。
4. 前端“自动重试成功”卡片当前实际显示的是当前已加载异常的 `retry_count` 总和，不等于成功重试次数，标题与统计口径不完全一致。
5. 前端“影响条数”当前固定显示 `1`，数据库没有独立的影响记录数或影响对象明细。
6. 异常类型中文映射当前仅覆盖 `TASK_EXECUTION`；代理、访问限制和超时类型会显示英文代码。
7. 异常趋势和“今日异常”基于前端一次最多加载的 100 条记录计算；待处理/已处理总数来自分页接口的 `total`，统计口径不完全一致。
8. 定时调度使用固定分钟间隔，不支持 cron 表达式；当前没有分布式租约，多 API 实例部署时存在重复调度风险。
9. 同一数据源只阻止同时存在 `RUNNING/CANCEL_REQUESTED` 任务，允许多个未来 `PENDING` 任务排队。

- 给原有 `crawl_task` 增加 6 个运行控制字段；
- 新增 `crawl_schedule`、`crawl_task_event`、`crawl_exception` 三张表；

- 在 Prisma 的 `DataSource`、`CrawlTask` 模型中增加关系导航字段。

注意：Prisma 中 `crawlSchedules`、`crawlExceptions`、`events`、`schedule` 等关系字段只是 ORM 导航属性，不是 MySQL 物理列。实际外键列位于关系的多方表中。

## 5. `data_source` 新增关系说明

`data_source` 本次没有新增 MySQL 物理字段，只在 Prisma 模型增加关系集合：

| Prisma 字段 | 是否数据库列 | 作用 |
| --- | --- | --- |
| `crawlSchedules CrawlSchedule[]` | 否 | 从数据源对象查询其所有定时计划 |
| `crawlExceptions CrawlException[]` | 否 | 从数据源对象查询其所有持久化异常 |

真实外键分别是 `crawl_schedule.data_source_id` 和 `crawl_exception.data_source_id`。

## 6. `crawl_task` 新增字段和关系

### 6.1 新增物理字段

| Prisma 字段 | MySQL 字段/类型 | 可空 | 功能作用 |
| --- | --- | --- | --- |
| `scheduleId` | `schedule_id INT` | 是 | 记录该任务由哪个定时计划生成；手动和异常重试任务通常为空。计划删除时设为 NULL，保留任务历史 |
| `runConfig` | `run_config JSON` | 是 | 保存本次任务的完整运行参数，包括触发来源、栏目、日期范围、分页、数量、超时、是否导入和重试来源 |
| `processPid` | `process_pid INT` | 是 | 当前 API 启动的爬虫主进程 PID，用于运行状态展示和停止控制；任务结束后清空 |
| `logPath` | `log_path VARCHAR(1024)` | 是 | 当前任务独立日志文件路径；API 读取日志时还会校验路径必须位于运行输出目录内 |
| `outputPath` | `output_path VARCHAR(1024)` | 是 | 当前任务独立 JSON、附件和中间产物根目录，避免多个任务共用输出目录 |
| `cancelRequestedAt` | `cancel_requested_at DATETIME(3)` | 是 | 用户请求停止任务的时间；用于区分主动停止与异常退出 |

### 6.2 `run_config` 当前内容

| JSON 字段 | 值/作用 |
| --- | --- |
| `trigger` | `MANUAL`、`SCHEDULE` 或 `RETRY` |
| `lookbackDays` | 增量任务回溯天数 |
| `startDate/endDate` | 范围任务日期边界 |
| `sections` | 四类栏目代码数组 |
| `pageSize` | 每页数量 |
| `maxRecords` | 每栏目最大公告数 |
| `maxPages` | 每栏目最大页数 |
| `timeoutMinutes` | API 超时分钟数 |
| `importData` | 是否执行数据库导入 |
| `retryOfTaskId` | 仅重试任务使用，指向原任务 ID；当前不是物理外键 |

### 6.3 新增关系和索引

| 项目 | 作用 |
| --- | --- |
| `schedule` | 通过 `schedule_id` 关联 `crawl_schedule.id`，删除计划时 `SET NULL` |
| `events` | 一对多关联任务事件；删除任务时事件 `CASCADE` 删除 |
| `exceptions` | 一对多关联任务异常；删除任务时异常的 `crawl_task_id SET NULL`，异常历史仍保留 |
| `INDEX(schedule_id)` | 加速按定时计划查询生成的任务 |
| `INDEX(status, scheduled_at)` | 加速调度器寻找到期 PENDING 任务 |
| `INDEX(data_source_id, status)` | 加速查找某数据源的活动任务和任务列表 |

### 6.4 任务状态含义

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 已创建，等待立即领取或预约时间到达 |
| `RUNNING` | 爬虫进程正在执行 |
| `CANCEL_REQUESTED` | 已请求停止，等待进程结束 |
| `SUCCESS` | 爬取及按配置执行的导入成功 |
| `PARTIAL_SUCCESS` | 已抓取到公告，但只有部分公告完成必需的结构化存储 |
| `FAILED` | 运行或导入失败 |
| `CANCELLED` | 用户主动取消完成 |
| `TIMED_OUT` | 超过任务指定超时时间 |

## 7. 新表 `crawl_schedule`

用途：保存可启停、固定间隔执行的采集计划。每次到期会创建一条独立 `crawl_task`。

| Prisma 字段 | MySQL 字段/类型 | 功能作用 |
| --- | --- | --- |
| `id` | `id INT AUTO_INCREMENT` | 定时计划主键 |
| `dataSourceId` | `data_source_id INT` | 计划所属数据源，外键到 `data_source.id`；数据源被引用时限制删除 |
| `name` | `name VARCHAR(128)` | 管理端显示的计划名称 |
| `taskType` | `task_type VARCHAR(32)` | 计划生成任务时使用的任务类型 |
| `intervalMinutes` | `interval_minutes INT` | 两次计划执行之间的固定分钟间隔，接口最小为 5 分钟 |
| `runConfig` | `run_config JSON` | 每次生成任务时复制的运行参数 |
| `isEnabled` | `is_enabled BOOLEAN` | 是否参与调度；关闭后保留配置但不再生成任务 |
| `nextRunAt` | `next_run_at DATETIME(3)` | 下一次应触发时间；调度器按该字段领取到期计划 |
| `lastRunAt` | `last_run_at DATETIME(3)` | 最近一次被调度器领取的时间，不代表任务一定成功 |
| `createdAt` | `created_at DATETIME(3)` | 创建时间 |
| `updatedAt` | `updated_at DATETIME(3)` | 最近更新时间，由 Prisma 自动维护 |
| `dataSource` | Prisma 关系字段 | 关联数据源，不是物理列 |
| `tasks` | Prisma 关系字段 | 查询该计划生成的任务集合，不是物理列 |

索引：`(is_enabled, next_run_at)` 用于扫描到期计划；`data_source_id` 用于按数据源查询。

## 8. 新表 `crawl_task_event`

用途：保存任务生命周期中的结构化事件，与原始文本日志互补。文本日志适合排查细节，事件表适合前端时间线和状态审计。

| Prisma 字段 | MySQL 字段/类型 | 功能作用 |
| --- | --- | --- |
| `id` | `id BIGINT AUTO_INCREMENT` | 事件主键 |
| `crawlTaskId` | `crawl_task_id BIGINT` | 所属任务，外键到 `crawl_task.id`；删除任务时级联删除事件 |
| `level` | `level VARCHAR(16)` | 日志级别，当前使用 `INFO`、`WARN`、`ERROR` |
| `eventType` | `event_type VARCHAR(32)` | 事件代码，如 `CREATED`、`STARTED`、`CRAWL_COMPLETED`、`COMPLETED`、`CANCEL_REQUESTED`、`CANCELLED`、`FAILED`、`TIMED_OUT` |
| `message` | `message TEXT` | 面向管理端和排障人员的事件说明 |
| `detail` | `detail JSON` | 可选结构化详情，如触发来源、进程 PID |
| `createdAt` | `created_at DATETIME(3)` | 事件发生时间 |
| `crawlTask` | Prisma 关系字段 | 关联任务对象，不是物理列 |

索引 `(crawl_task_id, created_at)` 用于按时间读取单个任务的事件时间线。

## 9. 新表 `crawl_exception`

用途：将可处理的异常持久化，支持待处理、重试、忽略、解决和审计。它不是原始日志表，也不应保存每一行普通日志。

| Prisma 字段 | MySQL 字段/类型 | 功能作用 |
| --- | --- | --- |
| `id` | `id BIGINT AUTO_INCREMENT` | 异常主键 |
| `dataSourceId` | `data_source_id INT` | 异常所属数据源，外键到 `data_source.id` |
| `crawlTaskId` | `crawl_task_id BIGINT NULL` | 关联任务；任务被删除时设为 NULL，仍保留异常审计记录 |
| `exceptionType` | `exception_type VARCHAR(32)` | 异常分类代码，当前类型见 3.1 |
| `sourceType` | `source_type VARCHAR(32)` | 异常来源对象类型：任务级 `CRAWL_TASK`、阶段级 `CRAWL_STAGE`、计划派发 `CRAWL_SCHEDULE` |
| `sourceRef` | `source_ref VARCHAR(256)` | 任务保存任务 ID；阶段保存 `{任务ID}:{阶段}`；计划保存计划 ID |
| `message` | `message TEXT` | 最新错误说明 |
| `status` | `status VARCHAR(32)` | `OPEN/PROCESSING/RESOLVED/IGNORED` |
| `retryCount` | `retry_count INT` | 从该异常点击重试并成功创建新任务的累计次数，不等于重试成功次数 |
| `handledBy` | `handled_by VARCHAR(128)` | 最后一次人工处理人；当前前端写固定文字“管理员”，尚未接用户账号 |
| `remark` | `remark TEXT` | 人工处理备注 |
| `resolvedAt` | `resolved_at DATETIME(3)` | 标记解决或忽略的时间 |
| `createdAt` | `created_at DATETIME(3)` | 异常首次创建时间 |
| `updatedAt` | `updated_at DATETIME(3)` | 最近错误重现或处理更新时间 |
| `dataSource` | Prisma 关系字段 | 关联数据源，不是物理列 |
| `crawlTask` | Prisma 关系字段 | 关联任务，不是物理列 |

约束和索引：

| 结构 | 作用 |
| --- | --- |
| 唯一键 `(source_type, source_ref, exception_type)` | 防止同一来源对象的同类异常重复插入；再次发生时更新原记录 |
| 索引 `(status, created_at)` | 加速按处理状态和发生时间查询 |
| 索引 `data_source_id` | 加速按数据源统计异常 |
| 索引 `crawl_task_id` | 加速按任务追溯异常 |

## 10. 已完成的异常闭环

1. 重试成功后通过 `run_config.retryOfTaskId` 自动解决原异常；失败或取消时恢复原异常为 `OPEN`。
2. 阶段失败写入 `CRAWL_STAGE` 异常，并保留阶段、任务、日志和输出目录定位信息。
3. 调度派发失败写入 `CRAWL_SCHEDULE/SCHEDULE_DISPATCH`；不会提前推进下次时间，成功派发后自动解决。
4. 重试任务、阶段初始化、创建事件和异常状态变化使用同一事务；`PROCESSING` 异常禁止重复重试。
5. 六阶段详细结构和统计口径见《爬虫数据处理漏斗与入库流水线说明》。

## 11. 后续改进建议

建议按以下优先级继续完善：

1. 为单条 RawNotice、RawNoticeAttachment、ProjectNoticeAttachment 增加对象级异常及只重放失败对象的处理器；目前导入失败先记录到所属阶段。
2. 修正前端统计名称和口径：把“自动重试成功”改成“已发起重试”，或真正按重试任务成功状态统计；增加真实 `affected_count` 或影响对象明细。
3. 补齐所有异常类型的中文展示映射，并由后端提供稳定的异常类型字典。
4. 如果部署多个 API 实例，为 `crawl_schedule` 增加数据库租约/调度锁，或迁移到独立任务队列。
5. 将 `handled_by` 接入登录用户身份，不再写固定“管理员”。
