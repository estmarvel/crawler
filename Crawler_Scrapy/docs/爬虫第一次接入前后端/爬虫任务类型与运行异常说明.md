# 爬虫任务类型与运行异常说明

> **已过时（2026-07-27）：** 本文保留初次接入时的设计过程，其中 `PARTIAL_SUCCESS` “仅预留”、前端尚未接入 SSE、增量回溯默认值等表述已不符合当前代码。当前任务类型、状态、日志、调度和异常以《数据库修改与接口变更汇总说明》为准。

## 1. 现状结论

原数据库和原代码没有对 `crawl_task.task_type` 给出完整类型定义：

- Prisma 中该字段只是 `VARCHAR(32)`，不是 enum。
- MySQL 迁移没有 `CHECK` 约束或字典外键。
- 《完整数据库文档》仅将其描述为“任务类型”。
- 当前数据库中的两条历史任务只使用了 `HISTORY_FULL`。

因此，下面三种类型是本次后端接口建立的应用层白名单，不是从原数据库中发现的既有枚举。数据库继续使用字符串，便于兼容现有数据；所有新建任务必须通过 API 校验。

## 2. task_type 类型

| 值 | 含义 | 必要参数 | 转换为爬虫参数 |
| --- | --- | --- | --- |
| `INCREMENTAL` | 增量采集最近若干天的数据 | `options.lookbackDays`，默认 1 | `--days N` |
| `HISTORY_RANGE` | 补采明确起止日期范围 | `options.startDate` 必填，`endDate` 可选 | `--start-date`、`--end-date` |
| `HISTORY_FULL` | 从最新页一直采到源站最后一页 | 无日期参数 | `--all` |

`MANUAL`、`SCHEDULE`、`RETRY` 不作为 `task_type`。它们表示任务的触发来源，保存在 `crawl_task.run_config.trigger`：

- `MANUAL`：通过接口人工创建。
- `SCHEDULE`：由 `crawl_schedule` 周期调度创建。
- `RETRY`：由异常重试接口创建，同时在 `retryOfTaskId` 保存原任务 ID。

这样可避免把“采集范围”和“触发原因”混在同一个字段中。

## 3. 任务状态

| 状态 | 含义 | 是否终态 |
| --- | --- | --- |
| `PENDING` | 已创建，等待预约时间或调度器执行 | 否 |
| `RUNNING` | Scrapy 子进程正在执行 | 否 |
| `CANCEL_REQUESTED` | 已收到停止请求，等待进程退出 | 否 |
| `SUCCESS` | 爬取及配置的数据导入步骤均成功 | 是 |
| `FAILED` | 爬虫启动、运行或数据导入失败 | 是 |
| `CANCELLED` | 人工停止完成，或启动前被取消 | 是 |
| `PARTIAL_SUCCESS` | 预留：部分栏目成功、部分失败 | 是 |
| `TIMED_OUT` | 超过 `run_config.timeoutMinutes`，受管进程被终止 | 是 |

当前两个站点由同一个 shell 入口运行，但一个数据库任务只启动一个站点，确保 `crawl_task.data_source_id` 与实际爬虫一一对应。同一数据源同时只允许一个正在运行的任务；多个未来预约任务可以排队。

每个 API 任务的 JSON、附件和日志写入独立的 `output/api_tasks/<taskId>`，但 `NOTICE_DEDUP_ROOT` 固定指向原全局输出根目录。这样不会因隔离输出而丢失跨任务去重能力。

## 4. 实时日志逻辑

原“实时采集日志”不是 Scrapy 实时日志。管理端 `CollectionCenter.vue` 每 30 秒请求一次 `/api/admin/collection`，后端把最近 `crawl_task` 记录转换为日志行；它只能展示任务结果摘要。

本次新增两种后端日志能力，前端页面暂未改动：

- `GET /api/admin/crawler/tasks/:id/logs`：返回结构化任务事件和日志文件末尾内容，适合轮询。
- `GET /api/admin/crawler/tasks/:id/logs/stream`：SSE 流，实时发送 Scrapy 标准输出、错误输出和状态变化。

完整过程日志保存于任务自己的 `log_path`；`crawl_task_event` 保存 `CREATED`、`STARTED`、`CRAWL_COMPLETED`、`COMPLETED`、`FAILED`、`TIMED_OUT`、`CANCEL_REQUESTED`、`CANCELLED` 等关键事件。避免逐行写数据库造成大量写入。

## 5. 异常处理

任务失败时写入或更新 `crawl_exception`，并通过 `(source_type, source_ref, exception_type)` 唯一约束防止同一任务重复产生多条相同异常。

异常状态为：

| 状态 | 含义 |
| --- | --- |
| `OPEN` | 待处理 |
| `PROCESSING` | 处理中或已创建重试任务 |
| `RESOLVED` | 已解决 |
| `IGNORED` | 经确认无需处理 |

重试会新建一个独立 `crawl_task`，不会复用或覆盖原任务；异常记录累计 `retry_count`，新任务的 `run_config.retryOfTaskId` 指向原任务。

## 6. 定时调度边界

`crawl_schedule` 当前使用 `interval_minutes` 实现固定间隔调度，最短 5 分钟，并持久化 `next_run_at`、`last_run_at` 和运行参数。API 进程每 15 秒检查一次到期计划。

当前未实现复杂 cron 表达式和分布式调度锁。单 API 实例可正常使用；若以后部署多个 API 实例，应增加数据库租约或独立任务队列，避免多实例同时调度。前端可按分钟、小时或天设置固定频率并换算为 `intervalMinutes`。`timeoutMinutes` 可选（接口允许 1～10,080 分钟，默认 720），超时会终止受管进程并生成异常记录。

API 直接复用 `Crawler_Scrapy/run_tws_history.sh`。当前部署使用 `CRAWLER_OUTBOUND_MODE=direct`，通过服务器公网 IP 访问，并启用单并发、5 秒随机延迟、AutoThrottle、零普通重试及首次连续 403/429 自动关停。`static` 和 `tianqi` 仍可作为备用；CONNECT 407 会归类为 `PROXY_AUTHENTICATION`，直连被限制会归类为 `ACCESS_BLOCKED`。
